# CLAUDE.md — Lunch Special

Daily Wordle-style game: guess the diner's "Special" (a world dish). 1950s diner theme. One Cloudflare Worker serves everything: React SPA (Workers Static Assets) + Hono API + D1. No accounts; player state in localStorage.

## Commands

```bash
npm run dev          # vite dev (Worker runs in workerd via @cloudflare/vite-plugin), http://localhost:5173
npm run play         # vite dev + opens /play: a fresh round on a RANDOM dish, nothing saved (dev-only free play)
npm run ramen        # same, but pinned to one named dish (/play?special=ramen) — playtest a specific board
npm run admin        # vite dev + opens /admin: straight to the login, skipping the game (password below)
npm test             # vitest — worker/**/*.test.ts + shared/**/*.test.ts (every pure fold has one)
npm run check        # tsc -b (3 project refs: app / worker / node)
npm run build        # tsc -b && vite build → dist/
npm run deploy       # build + wrangler deploy
npm run db:migrate   # apply migrations to LOCAL D1   (db:migrate:remote for prod)
npm run db:seed      # run seed/seed.sql on LOCAL D1  (bootstrap only — see warning below)
npm run db:export:remote    # dump PROD D1 → backups/prod-full-<stamp>.sql (gitignored). Take one before any prod DB work
npm run db:export:catalog   # same, but dishes+clues+schedule only — no player data, safe to diff against seed.sql
npm run db:export           # local DB, all tables
npm run cf-typegen   # regenerate worker-configuration.d.ts after wrangler.jsonc changes
```

Local admin password: `ADMIN_PASSWORD` in `.dev.vars` (gitignored; currently `lunchboss`). Browser preview: `.claude/launch.json` has server name `lunch-special`.

## Deploy to Cloudflare

**Live:** https://lunchspecial.app (custom domain on the Worker) — bootstrap is done and releases are automated (see CI below). The steps below are the record of that setup and what you'd repeat to bootstrap a fresh environment.

### One-time bootstrap (manual — touches the CF account + secrets)

1. `npx wrangler login` (logged in as the project's Cloudflare account)
2. `npx wrangler d1 create lunch-special-db` → paste returned UUID into `database_id` in wrangler.jsonc. Commit it — DB ids are not secret. (Prod id `f331205d-c816-48c9-b099-0fb15b7605ba` is already set.)
3. `npm run db:migrate:remote && npm run db:seed:remote` (seed once, by hand — see CI note below)
4. Set the two Worker secrets directly (interactive prompt — you type the value; run in your own terminal): `npx wrangler secret put ADMIN_PASSWORD` then `npx wrangler secret put SESSION_SECRET` (a long random string, e.g. `openssl rand -hex 32`). They persist across deploys, so CI never touches them.
5. First deploy by hand to confirm it works: `npm run deploy` → https://lunchspecial.app
6. Verify: play a guess on the live URL, log into /admin

### Where secrets live

- **Worker secrets** (`ADMIN_PASSWORD`, `SESSION_SECRET`, `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`): set directly on the Worker via `wrangler secret put`. They live on the Worker and persist across deploys, so CI never needs them. The Discord pair is **optional** — without it every deployment still runs, minus the Activity's Rich Presence (`/api/discord/token` answers 503). The client *id* isn't secret (it already ships in the bundle as `VITE_DISCORD_CLIENT_ID`); it's a Worker secret only so the pair stays together and no app id is hardcoded in the repo.
- **CI credentials** (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`): stored as **GitHub Actions secrets** (Settings → Secrets and variables → Actions).
  - `CLOUDFLARE_API_TOKEN` — a CF API token with the "Edit Cloudflare Workers" template scope + D1:Edit
  - `CLOUDFLARE_ACCOUNT_ID` — `9016037cfaa0836d9bbc85d754935cb5`

### Automated releases (CI)

Three workflows, deliberately scoped so routine pushes don't pay for the full gate:

| Workflow | Fires on | Does |
|---|---|---|
| `ci.yml` | push + PR to `main` | `npm test` → `npm run check` |
| `codeql.yml` | push + PR to `main`, weekly cron (Mon 04:27 UTC) | security-and-quality scan |
| `deploy.yml` | `v*` tag, or manual dispatch | test + check + remote D1 migrate + deploy |

`ci.yml` and `codeql.yml` both **skip prose/asset-only changes** via an identical `paths-ignore` (`**.md`, `docs/**`, `discord-assets/**` — none are covered by vitest or any tsconfig project). Keep the two lists in sync; Actions doesn't support YAML anchors. Both also set `concurrency` with `cancel-in-progress: true`, so a follow-up push supersedes the in-flight run instead of racing it. **If CI ever becomes a required status check, `paths-ignore` will hang doc-only PRs on "Expected — waiting for status"** — switch to an always-running gate job at that point.

`deploy.yml` deploys on any pushed tag matching `v*` (and via manual "Run workflow" / `gh workflow run deploy.yml`). Steps: `npm ci` → write a placeholder `.dev.vars` → `npm run cf-typegen` → `npm test` → `npm run check` → remote D1 migrate → `npm run deploy`. It re-runs test+check on purpose — the deploy gate shouldn't trust that CI already passed on some earlier commit. All three use `actions/checkout@v7` + `actions/setup-node@v7` on Node 22. Cut a release with:

```bash
git tag v1.1.0 && git push origin v1.1.0
```

CI gotcha: `worker-configuration.d.ts` and the `Env` secret members are generated from `.dev.vars` — both gitignored — so the workflow regenerates types (`cf-typegen`) and writes a dummy `.dev.vars` before the typecheck/build, or `tsc` fails on missing runtime types / `Env` members. That placeholder is **derived from the committed `.dev.vars.example`** (`grep`+`sed`, identical in ci.yml and deploy.yml) rather than spelled out: it used to be two hardcoded lists, and adding `DISCORD_PUBLIC_KEY` broke the typecheck on exactly that. **So a new Worker secret must be added to `.dev.vars.example`**, or CI can't see it.

CI runs migrations (idempotent, additive) but **never** the seed — `seed/seed.sql` DELETEs and re-inserts every dish, which would wipe admin edits. Seed only by hand, once, during bootstrap.

### Prod D1 is the only copy of half the data

`seed.sql` + `migrations/` reconstruct the dish **pool** and nothing else. The `schedule` (booked in /admin, not in this repo — never add `INSERT INTO schedule` rows), every admin dish edit, `analytics_rounds`, `analytics_visits`, `dish_requests`, `announcements` and `experiments` live **only** in prod D1 and have no repo representation. Divergence between the dashboard and `seed.sql` is therefore expected and correct, not drift to reconcile.

Two consequences: (1) `npm run db:seed:remote` is destructive — its `DELETE FROM schedule` deliberately steps around the `schedule.dish_id` FK that would otherwise block the dish wipe, so a stray run replaces every hand-booked Special with the stock 30-day block and reverts all admin edits; (2) there is no automatic backup. Run `npm run db:export:remote` before any prod DB work. Dumps land in gitignored `backups/` — full dumps carry anonymous `player_id` UUIDs, so keep them local; use `db:export:catalog` for anything you'd share.

Note: the vite plugin writes a build-processed config into dist/; plain `wrangler deploy` from the repo root picks it up (the `deploy` script already chains build first).

## Discord Activity

The game also runs as a **Discord Activity** (embedded iframe app) — **no separate build**. Discord doesn't host the code; it frames `lunchspecial.app` through its proxy via a URL mapping. So the same `npm run build` / `npm run deploy` ships both the public site and the Activity. The only Discord-specific client code is `src/discord/`, activated purely at runtime.

- **Detection:** `isDiscordActivity()` checks for the `frame_id` query param Discord adds to the iframe URL. On the open web it's absent, so `initDiscord()` returns null and the Embedded App SDK (`@discord/embedded-app-sdk`, behind a **dynamic import**) is never downloaded — zero cost to web visitors.
- **Boot:** `src/main.tsx` awaits `initDiscord()` before mounting React. When embedded, it completes the SDK `ready()` handshake, then the existing game runs **anonymously** exactly as on the web (localStorage state, no accounts). The only OAuth taken is the pair Rich Presence needs (`identify` + `rpc.activities.write`, see below), and the user object it hands back is discarded, so there is still no per-user identity anywhere in the app.
- **Sharing inside the Activity posts the check to the channel** (GitHub #108), falling back to the clipboard. Three hops in `src/discord/share.ts`: draw the score card as a PNG → upload it via `POST /api/discord/attachment` → `sdk.commands.openShareMomentDialog({ mediaUrl })`. Six things are load-bearing:
  1. **The fallback is the whole safety argument.** Before this, every Discord player got `copyShareText()` and a "paste it in chat" label; that is still exactly what a failure at any hop produces, so trying and failing is never worse than not trying. `shareToChannel()` never throws and returns a boolean; `ResultModal.share()` reads it and copies on false.
  2. **It's a picture, because the dialog takes a picture.** `openShareMomentDialog` accepts a Discord CDN URL and nothing else. What the card says is a pure fold in `shared/scorecard.ts` (`buildScorecard`, unit-tested), drawn by `src/game/scorecard.ts`. **The card never names the dish** — same rule as presence, same style of test, because it lands in a channel where most people haven't played yet.
  3. **Tiles are drawn as rects, not emoji.** The shared *text* uses 🟩🟨⬜ because it has to survive being pasted anywhere; a canvas doesn't, and `fillText` on an emoji hands the job to whatever font the device has. The palette is hard-coded from base.css rather than read from CSS at draw time — the image outlives the stylesheet that made it.
  4. **The upload goes through the Worker, and needs no new scope or bot token.** Discord's attachment endpoint takes a **user bearer of any scopes**, so the token the presence flow already obtains is the one that posts the card. The Worker makes the call because everything the iframe fetches is a relative `/api/*` (see the proxy note below). It stores nothing — no token, no image. Unconfigured deployments answer **503**, like `/token`.
  5. **Sharing never raises a consent sheet.** `canShareToChannel()` reads `peekToken()` rather than calling `ensureAuthorized()`, so a player who declined authorization for presence isn't asked again at the check — they just get the clipboard.
  6. **The button doesn't promise a destination.** Which path runs is only settled at click time, so the idle label is "📤 Share" and the *result* says where it went ("Sent to the channel!" vs "Copied — paste it in chat!"). `shareLabel()` in GamePage.tsx is the one place that wording lives.
  - `copyShareText()` tries `navigator.clipboard.writeText` and **falls back to a hidden-textarea `document.execCommand("copy")`**. That fallback is the point: `navigator.clipboard` is gated behind the `clipboard-write` permissions policy, which Discord's iframe doesn't grant, so the modern API alone just rejects there. `execCommand` only needs a user gesture. It returns a boolean and the button shows a retry label on `false` — never let a share fail silently.
  - **Previously tried and reverted:** `sdk.commands.shareLink({ message })` (Discord's own share modal, posts as the player with a deep link back into the Activity). It kept erroring in practice — the button just showed the retry label. Don't reach for `shareLink` again; `openShareMomentDialog` is the path that's wired now. (An older note here called that one "web-only" — Discord's current docs don't say so, which is why it was retried.)
  - **`shareInteraction` is not the answer either**, at least not cheaply: it's absent from Discord's published guides, and its request schema (`command`, `components[].custom_id`) implies a registered application command plus an interactions endpoint with Ed25519 verification. Only worth that if the share-moment path turns out to be unavailable.
  - **The 5s `ready()` cap must not gate anything but the mount.** The cap only decides *when React mounts* so a stalled handshake doesn't white-screen the iframe; a handshake landing at 5.1s is still a perfectly good SDK. The original #49+#51 shape registered the instance only on the race's winning branch, which silently killed the share button on every slow Activity start — which is why `attachPresence`/`attachShare`/`attachSocial` are all called inside the handshake's own `.then()`, not on the branch that wins the race.
- **Rich Presence** (GitHub #101): the player's Discord profile shows which mode they're in and how far through the guesses they are — "Playing Lunch Special / Today's Special · No. 26 / Guess 3 of 6", with an elapsed timer. The copy is a pure fold in `shared/presence.ts` (`buildPresence`, unit-tested in presence.test.ts); the SDK plumbing is `src/discord/presence.ts`; `GamePage` calls `setPresence()` from an effect keyed on round status + guess count. Six things are load-bearing:
  1. **It never names the dish.** A profile is read by people who haven't played today, so the answer, the guessed dishes and the clues are all barred from those two lines — the same rule as "never leak the target except via /reveal". Progress is safe; a guess count says nothing about what the dish is. A test asserts the fold's whole output space stays inside a character class no dish name can survive.
  2. **Two scopes, and `identify` is required — measured, not assumed.** The flow lives in `src/discord/auth.ts` (`ensureAuthorized`), shared with the score-card upload; presence keeps only its throttle. `rpc.activities.write` grants `setActivity`; `identify` is what the `authenticate()` hop needs, because the SDK parses its reply against a schema where `user` (username, discriminator, id, public_flags) is required and non-optional. Presence shipped on the single scope and never appeared on a profile; the fix changed *two* things at once (added `identify`, started sending `type: 0`), so #106 cut the scope back alone with `type` retained — and presence went silent again. Both: works. One: dead. **That experiment is finished; don't re-run it.** The cost is real (username/avatar/banner on the consent sheet of a game with no accounts), which is why it was checked. What it buys is Discord's handshake and nothing else — **the user object is dropped on the floor**, never read, stored, sent to the Worker, or written to localStorage, so the game stays anonymous. Don't add a third scope, and don't start reading the one we're forced to take.
  3. **The token exchange is server-side** (`worker/routes/discord.ts`, `POST /api/discord/token`): the SDK's `authorize()` yields a code, and trading it for an access token needs the client secret, which must never reach the browser. Unconfigured deployments answer **503** and the game is otherwise unaffected — presence is a flourish on someone else's profile and nothing may ever wait on it.
  4. **Authorize once per page load, whatever happens.** `prompt: "none"` keeps it silent for anyone who has authorized before; a refusal or a broken exchange sets `unavailable` and is never retried. Re-asking on the next guess is harassment, and a consent sheet mid-round is worse than no presence.
  5. **Throttled to one update per 4s with a trailing send**, because Discord's RPC limit is 5 SET_ACTIVITY per 20s and a burst would drop the *interesting* update (the win) rather than the noise. Identical activities are dropped by comparing the serialized payload, and a failed send clears that memo so the same state can be retried.
  6. **The elapsed timer measures this sitting and is dropped once the round ends.** A board restored from localStorage was begun on a page load we no longer have, so dating the timer to the round would report hours; and a counter still climbing beside "Solved it in 4 guesses" is measuring how long the tab stayed open. Preview and playtest publish nothing, gated on the same `tracked` flag as the beacons.
- **The footer's side pages already work in the embed — leave them alone.** `/privacy`, `/terms` and `/press` are plain same-origin links with no `target="_blank"`, so they navigate the iframe, Discord's proxy serves them from lunchspecial.app, and each page carries its own "← Back to the diner". `openExternalLink` was tried here (#108) on the theory that a sandboxed iframe kills them; it doesn't, because nothing in the game opens a new tab in the first place. The one real cost is that the return trip lands on a `frame_id`-less URL, so presence stays quiet until the next mode switch — not worth a rewrite. **The game currently has no outbound links at all**, and announcement bodies aren't going to grow any, so `openExternalLink` has no user. If one ever appears, that's the moment to reach for it.
- **Portrait lock on mobile** (GitHub #108): `lockPortrait()` in bootstrap.ts calls `setOrientationLockState({ lock_state: PORTRAIT })` on handshake (no OAuth scope; desktop ignores it). The board is a portrait menu card laid out for 375px, and the check is the tallest thing in the game at that width — a rotated phone hands the Activity a viewport a few hundred pixels tall. Every other surface lets the player choose that; the Activity is the one place we can decline. PIP and grid lock states are deliberately left unset: those tiles are too small to play in at any orientation.
- **The live progress message** (GitHub #108) — the Activity's growth loop, modelled on what Wordle's Activity actually does. On the player's **first guess** the app posts one message into the channel they launched from: their name and face, a picture of the board, and a **Play now!** button. Every guess after that **edits that same message**, and the round ending flips its text to the past tense. A whole round costs the channel one message, so nobody is spammed, and anyone scrolling past sees a game in progress and a one-click way into their own. Client half is `src/discord/progress.ts`, server half is `/api/discord/interactions` + `/api/discord/progress`. Eight things are load-bearing:
  1. **The message is created by Discord, not by us.** `shareInteraction({ command: "progress", options: [{name:"handle"}], require_launch_channel: true })` asks Discord to invoke *our* application command; Discord posts a signed interaction to `/api/discord/interactions`; the reply composes the message. That round trip is the point — it's what makes the next item true.
  2. **Identity is read from Discord's signed payload and never from the client.** The name and avatar come off the interaction, so a player can't make the app announce somebody else. `worker/avatar.ts` (`avatarUrl`/`displayName`, unit-tested) builds the URL; **Discord fetches the picture, so no avatar bytes ever pass through this app.** Default avatars index off the snowflake (`(id >> 22) % 6`, BigInt — `Number` silently rounds and collapses everyone onto one face) and animated `a_` hashes must be requested as `.gif`.
  3. **Nothing personal is stored, and that's a mechanism rather than a policy.** `discord_messages` (migrations/0022) holds `{opaque handle, interaction token, created_at}` and nothing else. It works because **edits never re-send `embeds`** — Discord replaces embeds wholesale, so the author line is written once at creation and left alone forever, while `content` and `attachments` (the tense and the card) are patched independently. Put the name in `content` and you would have to store it to re-send it.
  4. **The handle is client-minted, opaque, and bounded** (16 bytes of hex, `HANDLE_PATTERN`). Not the Discord user id, not the channel. The row expires because Discord kills interaction tokens at 15 minutes — expiry is structural, and the sweep-on-write is tidiness rather than the thing that makes it true.
  5. **The interaction token never reaches the browser.** Signing it into a client-held cookie would be cheaper than a table, but that token is permission to post as this app in someone's server. The table is the smaller mistake.
  6. **Verify the signature or don't answer.** `worker/discordsig.ts` (`verifyDiscordSignature`, unit-tested against real Ed25519) checks the **raw** body — re-serializing parsed JSON changes the signed message and fails every request. Discord validates a newly-saved endpoint by sending a deliberately bad signature and requiring a 401, so a 401 there is a passing grade.
  7. **Updates are trailing, not queued, and one failure retires the round.** Three guesses landing during an upload should show the third, not all three: the message shows a *position*. A failure retires the loop rather than retrying into Discord's rate limits, and a 410 (token expired on a slow round) retires it silently — the player must never learn any of this happened.
  8. **`resetProgress()` is declared above the publisher in GamePage.** Effects fire in order, and a board restored from localStorage publishes on mount; reset it afterwards and that post is orphaned, with the next guess posting a second message for the same round. Switching channels works for free — a new launch is a new round is a new message, where the player now is.
  - **Setup is manual and one-time**: `npm run discord:register` (needs `DISCORD_APP_ID` + `DISCORD_BOT_TOKEN` in the environment) registers the command, then set the portal's Interactions Endpoint URL to `https://lunchspecial.app/api/discord/interactions` and put `DISCORD_PUBLIC_KEY` on the Worker. **The bot token is used by that script and nowhere else** — it is not a Worker secret and nothing in the running app has one.
  - **`shareInteraction` is undocumented.** Every field above is read off its zod schema, not Discord's guides. It fits Wordle's observed behaviour exactly, but the first real test could disprove it — in which case the manual share button below still works and only the loop is lost.
- **The room the game is in** (GitHub #108) — three small runtime facts, all in `src/discord/social.ts`, none taking an OAuth scope, all no-ops off Discord:
  1. **Invite the table.** `openInviteDialog()` on a `replay-btn` in the check's footer. Discord's own guidance is that invites belong at the moment the experience wants company, not on the start screen. Hidden when `sdk.guildId === null` (DMs throw `INVALID_CHANNEL`); a player without `CREATE_INSTANT_INVITE` gets a swallowed error rather than a pre-flight `getChannelPermissions`, which would cost a **third scope** to pre-empt one failure.
  2. **"3 others are at the counter"** — `getActivityInstanceConnectedParticipants()` plus an `ACTIVITY_INSTANCE_PARTICIPANTS_UPDATE` subscription, rendered as a `counter-bar` above the menu header. Two rules: **only the count leaves the module** (the payload carries usernames, avatars and nicknames, and reading any of them would put identity into a game that has none), and **you are subtracted and the bar hides at zero** — "1 person here" names an empty room, which is worse than saying nothing.
  3. **Compact layout in picture-in-picture.** `ACTIVITY_LAYOUT_MODE_UPDATE` stamps `<html data-discord-layout="pip">` and game.css strips the board to the guess input, the tally and the rows. PIP stays **interactive**, so this is a board you can still order from rather than a thumbnail — which is why the input survives and sits above the history that scrolls away beneath it. An attribute rather than React state because PIP is a property of the window, not the round, and everything that changes is CSS. Three things are deliberate: **scoped to the attribute, not a width query** (a tile and a narrow phone share a width but not a situation — the phone is the game's main surface and keeps its whole card); the fixed backdrop layers are **display:none**, because a blurred full-viewport filter painting behind a card that now covers the tile is the most expensive thing on the page for no pixels anyone sees, and `.scene` takes the teal itself instead; and the header goes because Discord already draws the app's name on its own PIP chrome. Verified at 340×190: no horizontal scroll, input fully in view.
- **Why it works with no proxy gymnastics:** the app is same-origin + self-contained — all client calls are relative `/api/*`, all assets/fonts/art are Worker-served (no CDNs). Discord's "route everything through the proxy" rule is satisfied automatically by a root URL mapping.
- **Client ID:** `VITE_DISCORD_CLIENT_ID` — a **public** build-time Vite var (ships in the bundle; NOT a secret; do not put it in `.dev.vars`). Local dev: add it to `.env.local` (gitignored; see `.env.example`). CI: set it as a repo Actions **Variable** (not secret) — `deploy.yml` passes it to the build.
- **localStorage caveat:** inside Discord it's sandboxed to the `discordsays.com` origin, so Activity players have a **separate** game history from lunchspecial.app. Acceptable for the anonymous MVP; unifying stats is the (future) OAuth path.

### Discord Developer Portal (one-time, manual — not in this repo)

1. Create an app → copy **Client ID** into `VITE_DISCORD_CLIENT_ID` (local `.env.local` + CI Variable).
2. Enable **Activities** in the app's Embedded settings.
3. Add **URL Mapping**: prefix `/` → `lunchspecial.app`.
4. Add an OAuth2 redirect URI (`https://127.0.0.1` placeholder is fine for the embedded flow).
5. For Rich Presence, copy the same **Client ID** and the OAuth2 **Client Secret** onto the Worker: `npx wrangler secret put DISCORD_CLIENT_ID` and `npx wrangler secret put DISCORD_CLIENT_SECRET` (plus the same two keys in `.dev.vars` for local dev — leave them empty and presence simply stays off). No portal toggle is needed: both scopes are requested at runtime, and the presence card shows the app's own icon, so nothing has to be uploaded under Rich Presence → Art Assets.

**Dev testing inside real Discord:** Discord can't reach `localhost`, so it needs a public HTTPS URL. Run `npm run dev` in one terminal and `npm run tunnel` (cloudflared quick tunnel → :5173) in another, then point the portal's URL Mapping at the printed `*.trycloudflare.com` URL while testing. (`cloudflared` must be installed separately.)

worker/index.ts       Hono entry; only /api/* reaches the Worker (assets serve the rest)
worker/game.ts        PURE game logic (feedback, puzzleNumber, date validation, fallback pick) — unit tested
worker/auth.ts        HMAC tokens: session cookie + preview tokens (stateless, SESSION_SECRET-signed)
worker/db.ts          row mapping, getTargetDish (schedule row else deterministic fallback), serverToday
worker/menu.ts        PURE menu-mix fold (schedule × dishes → region/course/protein ratios) — unit tested
worker/announcements.ts   PURE notice logic (status, audience eligibility, input validation) — unit tested

worker/growth.ts      PURE all-time growth fold (hour buckets → zero-filled ET-day series + least-squares trend) — unit tested
worker/countries.ts   PURE country-mix fold ((country, player) rows → one country per device + untracked) — unit tested
worker/rhythm.ts      PURE weekday × hour fold (same all-time hour buckets → 7×24 heat grid + both marginals) — unit tested
worker/dishstats.ts   PURE per-dish fold (rounds grouped by dish_id → win rate / guesses / DNF / shares per dish) — unit tested
worker/experiments.ts PURE all-time daily series fold (hour buckets + player activity → zero-filled raw per-ET-day rows) — unit tested
worker/funnel.ts      PURE player-funnel fold (same (player, hour) rows + visits by day → per-device stages) — unit tested
worker/discordsig.ts  PURE-ish Ed25519 check that an interaction really came from Discord (raw body!) — unit tested
worker/avatar.ts      PURE Discord avatar url + display name (default faces, animated hashes) — unit tested
worker/device.ts      PURE one-device fold (grouped rounds + visits + notice views → the review shown before a wipe) — unit tested
shared/markdown.ts    PURE inline-markdown tokenizer for announcement bodies (bold/italic/link → tokens, never HTML) — unit tested
shared/presence.ts    PURE Discord Rich Presence copy (round → "Today's Special · No. 26" / "Guess 3 of 6"; never the dish) — unit tested
shared/scorecard.ts   PURE shareable score card (round → title/subtitle/tile rows; never the dish) — unit tested
shared/sample.ts      PURE small-sample statistics — Wilson intervals, SMALL_SAMPLE_MIN, weighted median/percentile — unit tested
shared/experiment.ts  PURE before/after comparison — windowing, pooled rates, verdicts, "how many more days" — unit tested
shared/time.ts        GAME_TIMEZONE (America/New_York), gameToday, msUntilGameMidnight — the midnight-ET daily rollover, shared by worker + client
worker/routes/discord.ts  /api/discord/token — OAuth code→token hop for Rich Presence (client secret never reaches the browser)
                          /api/discord/attachment — forwards the score-card PNG to Discord's attachment endpoint (the

## Game rules (server-enforced shapes in shared/types.ts)

- 6 guesses; clue N returned by POST /guess after miss N (N=1..5, from `clues.order_index`)
- Feedback: ingredient set intersection + 4 attribute tiles. Country: hit=same country, near=same `region`, miss. Course/temperature/protein: hit|miss
- Date = the current puzzle date (YYYY-MM-DD), which **rolls over at midnight ET (`America/New_York`) for everyone**, not the browser's local midnight or UTC — `gameToday()` in shared/time.ts, used by both the client (`localToday`) and the worker (`serverToday`). Server accepts a **playable date** — today (±2 days of ET now for clock/rollover slack) or any earlier puzzle back to EPOCH_DATE. Future dates beyond the ±2-day window are rejected so upcoming Specials aren't spoiled (`isPlayableDate` = `isAllowedRequestDate` ∪ `isArchiveDate` in worker/game.ts). Puzzle #1 = 2026-07-17 (EPOCH_DATE). The player's "Next Special in …" and the admin dashboard's "Switches in …" both count down to the next midnight-ET via `msUntilGameMidnight`
- **Archive** (play previous days): `?date=<past puzzle>` on / replays an earlier Special. Client shows a "Menu Archive" calendar (unlocked once today's Special is finished) of every puzzle EPOCH→today with per-day status. Archive rounds persist per-date in `localStorage` (`lunch-special:archive`) but do **not** touch lifetime Stats/streak (Wordle-style). They **do** record anonymous analytics as the `leftover` kind — one of three round kinds (`daily` = Today's Special, `leftover` = archive replay, `random` = Chef's Choice) the admin dashboard breaks "games started" down by (migrations/0007, worker/routes/analytics.ts + admin `/analytics`). See src/game/ArchiveModal.tsx + archive.ts + storage.ts.
- **New vs returning players**: the `/start` beacon carries an anonymous, stable per-device `player_id` (random UUID in `localStorage` key `lunch-special:player`, via `getPlayerId()` in storage.ts; migrations/0008). The admin `/analytics` folds each player's active ET days: their earliest day counts them as **new**, every later active day as **returning** (all-time `players.new` = distinct players ever, `players.returning` = those who came back). The dashboard shows today's new/returning counts and an all-time two-line chart (`PlayerLineChart` in Dashboard.tsx). Anonymous device count only — no accounts.
- **Repeat visits** (admin **Players** tab): the restaurant read on top of new-vs-returning — of the players who have visited N times, how many came back for an N+1th? A **visit is an ET day the device played on**, not a round (four leftovers in one sitting is one visit), which is why the fold reuses the same `activeDaysByPlayer` sets `foldPlayerActivity` already builds. All pure in `worker/players.ts` (`foldRetention`, unit-tested in players.test.ts), rendered by `RetentionCurve` in PlayersPanel.tsx. All-time and surface-filtered; **always folded against the real `today`, never the picked day** — the window asks "has enough time passed by now", and answering it from a past day would call every visit since then a no-show. Four things are load-bearing:
  1. **Censoring.** A player only enters rung N's denominator once `RETENTION_WINDOW_DAYS` (7) have passed since their Nth visit. Without it a busy week *lowers* retention, because it adds players who cannot yet have returned. The ones still inside their window are reported as `pending`, beside the rung — never silently dropped, and never counted as no-shows.
  2. **A fixed window, not "ever".** `returned` means a next visit *within* the window, so every player in a denominator had the same amount of time. Counting any later return would make the number track the age of the audience instead of the game. Genuine slow returns aren't discarded — they land in `lateReturned`, shown as "+N came back later".
  3. **Tracks, not a funnel** — same rule as `FinishRate`: each rung's track *is* its own cohort and the fill is the answer, so no row is the always-full first bar. Shrinking cohorts are stated as "17 of 50", not re-encoded as bar width.
  4. **Teal, because teal already means "returning player"** on the line chart above and the player tiles. Not the kind palette (game mode), not the event palette (start/finish/share).
  Thin cohorts are flagged inline ("small sample") rather than hidden — "how many of my three-timers came back" is the question, and a blank row answers it worse. But the prose headline sentence is **suppressed** until both of the first two rungs clear `RETENTION_MIN_COHORT` (10), the same way `paceNote` refuses a percentage off a baseline under one game: a rung can quote 1-of-1 because it prints its denominator, a sentence can't.
- **Growth chart** (admin Trends tab, the first panel): the **running total** of games played per ET day since the first round ever recorded, every kind together, with a straight constant-pace line through it (GitHub #90). It rides `AnalyticsSummary.growth` and is folded from the **same all-time hour buckets** `rhythm`/`activeDates` already read, so it costs no extra query — pure in `worker/growth.ts` (`foldGrowth`, unit-tested in growth.test.ts), drawn by `GrowthChart` in TrendsPanel.tsx. Six things are load-bearing:
  1. **Cumulative, not per-day.** The question is popularity over months, and a per-day series answers it in day-of-week noise. The cost of a curve that can only rise is that "it's going up" stops being information — so everything else here exists to make the **bend** legible. Don't "fix" it into a per-day chart; that's the spark below it.
  2. **All-time, not the `daily` series.** `daily` stops ~5 weeks back; growth is exactly the thing a moving window can't show. It sits above the 30-day spark rather than replacing it — the spark answers "what are they playing", this answers "is the game gaining".
  3. **The dashed straight line is the reference the bend is read against** — the least-squares fit *through the cumulative curve*, i.e. the same run at one constant pace. Curve above it at the right = gaining, sagging below = stalling. Without it a cumulative chart is unreadable, because every cumulative chart looks like success.
  4. **The fit is clipped, never clamped.** An accelerating run's best-fit line crosses zero *before* day one, so `trend.first` is routinely negative and the line legitimately exits the plot bottom-left (`clipPath` in the SVG); pinning it to the axis would flatten the pace it exists to state.
  5. **The headline states two measured paces, never a forecast.** `growthNote()` compares `recentPerDay` (the actual rate over the last `GROWTH_RECENT_DAYS` = 7, straight off the running total) against `slope` (the all-time average), and only calls it gaining/losing outside a ±`GROWTH_STEADY_BAND` (15%) band. No line at all under `GROWTH_TREND_MIN_DAYS` (7), the rule `paceNote` follows for a thin baseline. A dead tail is "Stalled", stated rather than divided.
  6. **The reference line is dashed ink, not a series hue.** It's an annotation over the data, not a second measurement, so it takes neither the kind palette nor the event palette. The curve is teal (the event palette's "start") with a same-hue area fill — accumulated mass, not a second value.
- **Country pie** (admin **Players** tab, last panel): where the audience actually is, all time (GitHub #92). The country is stamped **server-side** on the beacon — `countryOf()` in worker/routes/analytics.ts reads `request.cf.country` (CF-IPCountry header as fallback), insert-only like `kind`/`surface`/`dish_id`, stored in `analytics_rounds.country` (migrations/0018). ISO 3166-1 alpha-2 plus Cloudflare's two non-countries, `T1` (Tor) and `XX` (unresolved). Still anonymous — no IP is stored, and the client sends nothing, so there's nothing to spoof. Rides `AnalyticsSummary.countries`, folded pure in `worker/countries.ts` (`foldCountries`, unit-tested in countries.test.ts), drawn by `CountryPie` in PlayersPanel.tsx. Five things are load-bearing:
  1. **It measures rounds started, not requests — and that's the whole point.** The beacon only fires from a browser that ran the game's JS, so a country busy in Cloudflare's request analytics but quiet here is traffic that never played. The **gap between the two dashboards** is the bot read; don't "fix" this by folding in raw request geography, which would erase it.
  2. **Devices are partitioned, one country each.** A device that played from two countries appears in two grouped rows, so a `COUNT(DISTINCT player_id) GROUP BY country` would sum to more than the audience — and slices that add to more than the whole are a lie the pie's shape tells. `foldCountries` assigns each device to the country it played most from (ties broken by code, so the fold doesn't depend on row order). That's why the query groups by `(country, player_id)` and the attribution happens in JS.
  3. **Rounds are printed beside every slice** because rounds-per-device is the bot tell: one device replaying 40 times is not a foreign crowd. Slices are devices; rounds are exact.
  4. **A pie, which is the exception here.** Justified because it's a whole cut into parts, asked once of one all-time total, with a handful of slices — and because the issue asked for distribution, not quantity. It takes a **single-hue teal ramp ordered by share**, not a categorical palette: mustard/teal/cherry already mean game kind and start/finish/share already mean event, and a pie can't be one hue the way the menu-mix bars are (there's no length to carry the value). The ramp restates the rank the slices are already sorted by, so it adds no fourth colour meaning; the pooled "Elsewhere" tail is grey, because everyone-else isn't a rank. Top `MAX_COUNTRY_SLICES` (8) get their own slice.
  5. **Pre-0018 rounds are `untracked`, never a slice.** "Not measured" is not a place, and dropping them silently would overstate every real share — same rule as the null player split. `countryUntrackedNote()` is the one wording. Country names come from `Intl.DisplayNames` (`countryName()` in analyticsUi), so no country table ships with the app.
- **Surface (web vs Discord)**: every beacon carries a `surface` — `web` or `discord` (`SURFACES` in shared/types.ts; migrations/0009) — resolved client-side once via `currentSurface()` in src/discord/bootstrap.ts (the `frame_id` signal, same as `isDiscordActivity()`). Set on insert only, like `kind`. Because mode switches navigate by assigning a URL (`goToday`/`goRandom`/`openArchiveDate`), which wipes the query string, Discord's iframe params are captured on first load into sessionStorage: `currentSurface()` reads that sticky copy, and every in-app URL goes through `surfaceUrl()` to re-attach them (so the SDK handshake also survives the hop). Skipping either made Chef's Choice / Leftovers log as `web` inside Discord. The admin dashboard's engagement panel has a **Web / Discord / All** segmented toggle (`SurfaceToggle` in Dashboard.tsx) that re-fetches `/analytics?surface=<web|discord>` (omit = all); the worker splices a whitelisted `surface = '…'` clause into every aggregate query. Pre-0009 rows default to `web`.
- **Day picker**: the engagement panel's day slice (the "Today's Special" block) defaults to today but a 📅 calendar dialog (`src/admin/DayPicker.tsx`) can swap in any earlier ET day — `GET /api/admin/analytics?date=YYYY-MM-DD`, which the worker returns as `day` (plus `today` and `activeDates`; the old `today: {…}` object field is now `day`). Only days in `activeDates` — ET days that recorded any round, derived from the same all-time hour buckets the hourly chart uses, so it honours the surface filter — are clickable. The day's `startedByKind` comes from its own ±1-day UTC window folded to ET, **not** from the `daily` series, which only reaches back ~5 weeks. All-time charts/tables and the activity feed are unaffected by the picked day.
- **Recent activity feed**: the admin dashboard's engagement panel ends with a log of the individual beacons behind the charts — newest first, with the ET wall clock + "3m ago", the event type (Started / Finished / Shared), game kind, dish + puzzle number, result (`Solved in 4` / `Out of guesses (6)`), surface, and the anonymous player id (`RecentEvents` in Dashboard.tsx, `GET /api/admin/recent-rounds?limit=&surface=`). **Don't rename that route back to anything matching `analytics/event`** — ad blockers ship filter rules for that path shape and cancel the request in-browser, which reads as a bare "NetworkError" with nothing in the Worker logs (GitHub #47 follow-up). Same reason `request()` in src/admin/api.ts translates a rejected `fetch` into a "check your ad/content blocker" message. `analytics_rounds` is still one row per round; the endpoint UNIONs it back into three event streams. migrations/0011 added `completed_at`/`shared_at` so finishing and sharing get their own timestamps — before it, `updated_at` was clobbered by whichever beacon landed last, so pre-0011 rows fall back to it and show both events at the same time. The feed names the dish from `analytics_rounds.dish_id` (migrations/0012), set on insert by the beacon handler (`resolveDishId` in analytics.ts): a `random` (Chef's Choice) dish is picked from the round's `seed` and is **never** in the `schedule`, so the old "join `schedule` on play_date" resolution could only show it blank — the client now sends `seed` on the start/complete beacons so the server can resolve and store the actual dish. Pre-0012 rows have NULL `dish_id` and fall back to the schedule-by-date join (random stays blank for those, as before).
- **At a glance** (admin **Today** tab): the day slice, carrying the reads a bare count can't give. It used to end with an all-time tile strip, which was the Players tab's opening row rendered twice — that (and the new/returning tiles, which the Players line chart says better) is now one sentence and a link. All of it folds out of one extra query shape — the day's ±1-day UTC window now buckets by hour *and* kind and sums completed/solved/shared, so `day` gained `hourly` (24 ET hours, each split by kind), `allKinds` (every mode, where `day.totals` narrows to the Special), `lastStartedAt`, and `pace`. The folds are pure in `worker/service.ts` (`foldDayService` / `foldPace`, unit-tested in service.test.ts). Five things are deliberate: (1) **`pace` averages only ET days strictly before the selected one, and only days that recorded rounds** — folding in the day itself mutes the deviation being looked for, and averaging in zero-round days would make every live day look like a record; it compares *cumulative through the current ET hour*, so a 9am glance isn't measured against a full day. (2) **Hours after "now" render faded, not empty** — on today they haven't happened, which is not the claim "nobody played then". (3) The pace line **disappears rather than divides by a baseline under 1 game** — a percentage off a fraction is noise. (4) **Two colour systems, never mixed.** mustard/teal/cherry are the *kind* palette (Special / Leftovers / Chef's Choice) on the hourly chart and every spark; the Activity feed's *event* palette (start = teal, complete = cherry, share = mustard) is what `FinishRate` fills use. Borrowing the kind hues for a completion rate — even permuted — makes a rate look like a game mode. (5) **`FinishRate` is two tracks, not a funnel**: each track *is* its denominator (started, then finished) and the fill is the answer, so no row is the always-full first bar a funnel wastes. The non-finishers are **split, not lumped** — `day.open` from `foldDayService` reports `inProgress` vs `abandoned`, decided by how old each start cohort is against `DNF_GRACE_MINUTES` (2h). This used to be one clamped "DNF" number, which mid-afternoon reads a full diner as a mass walkout: on a live day most of that gap is people still playing. The floor stays because start and complete are independent beacons and a `/complete` whose `/start` never landed can briefly outrun starts. `DNF_NOTE` in analyticsUi is the one wording; `difficultyNote()` is shared with the Players tab so the same number can't be worded two ways.
- **Menu mix** (admin **Menu** tab, under the dish report): what the *kitchen* has been serving, as opposed to what players did with it. `GET /api/admin/menu-mix` joins `schedule` × `dishes` and hands every row to the pure `assembleMenuMix()` in worker/menu.ts (unit-tested in menu.test.ts); `src/admin/MenuMixPanel.tsx` charts it. Three slices — **served** (schedule rows EPOCH→today), **booked** (future rows), **pool** (active dishes) — each counted by region / course / protein / temperature, plus countries, a top-ingredients "pantry", repeat dishes, and a region-cadence strip over the last 60 Specials. No player data, so it takes no `surface`/`date` filters and no analytics tables. Two things to preserve if you touch the charts: (1) **every bar is one hue** — these are nominal categories, so bar length already carries the value and nine region colours would just re-encode it; (2) the grey tick on a bar is the **pool's** share of that category, which is what makes over/under-serving visible without a second series. Days from EPOCH with no schedule row ran on the deterministic fallback pick and can't be reconstructed (the pool moves), so they're reported as `unscheduledDays` rather than folded into `served`.
- **Dashboard tabs** (`src/admin/Dashboard.tsx`): six tabs, each holding one **question** rather than one data source. That distinction is the fix for how they were first split — Overview and Players both rendered the day slice, while Trends carried the audience charts (retention, country) that had nothing to do with time. Left to right: **Today** (operational — what's live, what's booked, today's service), **Menu** (what we serve *and* how it lands), **Players** (who's playing: the day's Special, all-time, the drop-off funnel, new-vs-returning, repeat visits, country), **Trends** (time only: growth, the 30-day spark, weekday profile, the heatmap, a collapsed daily table), **Experiments** (did anything we did cause any of it), **Activity** (the raw beacon feed). The URL mirrors the tab in `?tab=`; the key for Today is `today` (it was `overview`, and an old bookmark just lands on the default, which is the same tab). Every tab is surface-aware now — **Menu is the mixed case**, where the toggle governs the dish report and not the catalogue mix, which the panel says out loud.
- **Small-sample honesty** (`shared/sample.ts`, unit-tested in sample.test.ts): this game records tens of rounds a day, so "67% win rate" off 3 completions and off 300 render identically and mean nothing alike. Every rate quoted off a denominator under `SMALL_SAMPLE_MIN` (30) carries its **Wilson 95% interval** beside it (`RangeHint` in analyticsUi; `.rate-range` in admin.css), and nothing else does — an interval on every number teaches you to ignore them, an interval on exactly the soft ones is a signal. **Wilson, not the normal approximation**, because the game lives where that breaks: tiny `n`, and rates pinned near 0 (nobody shares) or 1 (almost everyone solves), where the textbook formula returns a zero-width interval — the most confident and most wrong thing a dashboard can print. The module also holds `separated()` (do two intervals overlap — deliberately conservative, so the dashboard says "different" *less* often than it strictly could) and weighted `medianOf`/`percentileOf`. The dashboard had this instinct in four ad-hoc places already (`RETENTION_MIN_COHORT`, `paceNote`'s `typical < 1` guard, `GROWTH_TREND_MIN_DAYS`, and now `DIFFICULTY_MIN_SOLVES`); this is that rule written once. **Don't quote a new percentage without deciding which side of it you're on.**
- **Dish report** (admin **Menu** tab, above the mix): how each dish actually *played* — win rate ±range, avg guesses, an inline guess-spread strip, share rate, DNF, times served. `GET /api/admin/dish-report` (surface-aware) groups `analytics_rounds` by `(dish_id, kind, completed, solved, shared, guesses)` and folds it pure in `worker/dishstats.ts` (`foldDishStats`, unit-tested in dishstats.test.ts); `src/admin/DishReportPanel.tsx` renders it. `dish_id` has been stamped on every round since migrations/0012 and **nothing aggregated it until this** — the feed used it to name a row and that was all, so the catalogue half of the dashboard and the outcomes half had no way to meet. Four things are load-bearing: (1) **every kind counts, not just `daily`** — a Leftover or a Chef's Choice is a genuine first attempt at that dish for that device (the archive shows a finished day's *result* rather than replaying it), and at this volume that's the difference between 30 attempts and 9; `byKind` rides along so a dish carried by replays is visible as such. (2) **Sorted hardest-first by loss rate**, not by popularity — a popularity sort just reproduces the schedule; dishes nobody completed sort *last*, because an unmeasured dish isn't a hard one. (3) The headline only names a hardest/easiest pair when their intervals **don't overlap** (`separated()`), and says so plainly when they do — at a few dozen rounds a dish those are usually the same dish with different luck. (4) Rows under `DISH_MIN_COMPLETED` (8) are dimmed, not dropped; rounds with a NULL or deleted `dish_id` are reported as `untracked` rather than assigned to anything.
- **Play rhythm** (admin **Trends** tab: "Which day of the week" + "When people play"): a 7×24 ET weekday × hour heatmap with both marginals, plus a weekday profile above it. Folded pure in `worker/rhythm.ts` (`foldRhythm`, unit-tested in rhythm.test.ts) from the **same all-time hour buckets** `growth`/`activeDates` already read — no extra query. It replaces the flat 24-hour bar chart, which alongside the 30-day spark was **one of two one-dimensional shadows of the same two-dimensional thing**; the interaction neither could show ("Sunday mornings are busy, Tuesday mornings are dead") is the only part that's a scheduling decision. `AnalyticsSummary.hourly` is gone — it's `rhythm.byHour`, the grid's column marginal. Three things are load-bearing: (1) **weekday figures are averages per occurrence, never totals** — a run that launched on a Friday has had one more Friday in it than Thursday, and at three weeks of history that head start alone invents a "big day"; the occurrence count is drawn on every bar and `WEEKDAY_MIN_OCCURRENCES` (3) hatches the ones too thin to quote. (2) A weekday that came around and recorded nothing **is in the denominator** — once the beacon is live, a quiet Monday is a measured zero. (3) The heatmap is **one hue varying only in intensity, and zero is an empty cell rather than the palest step** — at this volume most cells are 0 or 1, and a ramp starting at "faint" makes an empty 4am look like a measurement.
- **Solve time** (admin **Players** tab, beside the all-time guess distribution): median and p90 minutes from `started_at` → `completed_at`, folded by `foldSolveTimes` in worker/service.ts. Recorded since migrations/0011 and unread until now. It's the difficulty signal guess count can't give — solving in four guesses after twenty seconds and after six minutes are different puzzles. **Median and p90, never a mean**: a round is a browser tab, and the ones opened at breakfast and finished at lunch are real rows that drag an average by minutes. Negative durations (a late `/start`) are dropped, not clamped — a "-3 minute" solve is a broken measurement, not a fast one.
- **Experiments** (admin **Experiments** tab): the change log the rest of the dashboard is measured against — one row per deliberate change, with the metric it was meant to move (`experiments`, migrations/0019). `GET /api/admin/experiments` returns the log **plus the all-time daily series**, and `src/admin/ExperimentsPanel.tsx` does the windowing and statistics client-side, so re-metricking or re-windowing any change costs no request. The fold is pure in `worker/experiments.ts` (`foldExperimentSeries`), the comparison in `shared/experiment.ts` (`compare`), both unit tested. Markers for each change are drawn on the growth curve and the 30-day spark in TrendsPanel. Six things are load-bearing:
  1. **"Too early to tell" is a verdict, not an absence.** At tens of rounds a day it's the *normal* answer for a fortnight, and a dashboard that can't say it will instead show a number that went up. Four states: moved-up / moved-down / no-change / inconclusive.
  2. **Every undecided verdict comes with `daysNeeded`** — roughly how much longer a `TARGET_LIFT` (20%) change would need to be visible, sized off the before-period's own noise and traffic. That converts "I don't know" into a date, and it's the single most useful thing a small-n dashboard can say. It's a rule of thumb (95%/80% two-sample sizing), not a pre-registered power analysis; the point is whether the answer is three weeks or three months.
  3. **The metric is named when the change is logged**, and reading a different one prints a warning. Picking the metric afterwards means picking whichever of six happened to wiggle — one of them always will have.
  4. **Rates are pooled over the period, never averaged across days.** A period's win rate is total solved over total completed; averaging daily percentages lets a one-round Tuesday outvote a whole weekend. That's also why the series ships **raw counts** — a pre-divided percentage can't be re-pooled over a different window.
  5. **Counts and rates get different tests.** A count's noise is day-to-day variance (two-sample t against the pooled spread, both sides needing ≥2 days); a rate's is binomial (non-overlapping Wilson intervals, deliberately stricter than a difference-of-proportions). Judging a rate by how much traffic wobbled would be the wrong question.
  6. **The ship day counts as "after"**, and the after-window is clipped at today — padding it with days that haven't happened would dilute the change being looked for. The before/after strip shows the *daily* values beside the two aggregates, because two numbers can't reveal that the "after" is one enormous day and six dead ones.
- **Visits — the funnel's top** (migrations/0020): a round counts as "started" on the **first submitted guess** (GitHub #27), which is the right definition and left everyone who loads the game and never guesses invisible. `POST /api/rounds/seated` fixes that: one row in `analytics_visits` per device per ET day, fired from GamePage when a real tracked board is ready (never preview/playtest). Five things are load-bearing:
  1. **The day and country are stamped server-side**, like `country` on the round beacons. A visit belongs to the ET day it happened on, which the client has no authority over, and there's nothing to spoof. The client sends only its anonymous device id and surface.
  2. **Two ledgers, again.** `markSeated()` in storage.ts (sessionStorage, keyed on the ET day) decides whether to *send*; the table's `PRIMARY KEY (visit_day, player_id)` decides what to *count*. Neither is sufficient alone — sessionStorage is per-tab and cleared often, and without it every mode switch (which navigates by assigning a URL) would refire.
  3. **Days before the beacon shipped are `null`, never 0.** `visited: null` means unmeasured; reporting 0 would claim a 100% bounce rate for the whole of the game's history. `FinishRate` omits its top row entirely on those days rather than drawing an empty one.
  4. **The funnel's first row counts people, the rows under it count games** — and that switch is what makes the arithmetic true. A visit is one device per day while `started` counts rounds, so a player doing the Special plus three Leftovers is one arrival and four starts; dividing those reports a 400% play rate. The top row is `players` (devices) over `visited` (devices); both rows name their unit. The same rule governs the `playRate` experiment metric, which skips any day missing *either* count.
  5. **A ratio over 100% is possible and only the bar is clamped.** The beacons are independent, so a round begun at 11:58pm files its start on the next ET day from the arrival before it, and a blocked visit beacon leaves a player who plainly played. The number stays honest; the fill is capped so the row still reads. Same discipline as the DNF floor.
  Adds `visitors` and `playRate` to `EXPERIMENT_METRICS`, which is the point: "did my change get more of the people who showed up to actually play" was previously unaskable.
- **Player funnel** (admin **Players** tab, "Where players drop off"): the whole journey in one shape — opened the game → made a guess → reached game over → shared *or* played another round. Rides `AnalyticsSummary.funnel`, folded pure in `worker/funnel.ts` (`foldFunnel`, unit-tested in funnel.test.ts) off the **same `(player, UTC hour)` rows the new-vs-returning fold already reads** (the query gained `COUNT/SUM` aggregates plus `MIN(completed_at)` / `MAX(started_at)`), so it costs no extra query. Drawn by `FunnelChart` in PlayersPanel.tsx. Six things are load-bearing:
  1. **Every stage counts devices, never rounds** — that unit is the only reason this is allowed to be a funnel when `FinishRate` isn't. A visit is one device per ET day while a "start" is a round, so a player doing the Special plus three Leftovers is one arrival and four starts: stacked as stages those *grow* as they descend. In devices each stage is a real subset of the one above. **The two coexist on purpose** — Today counts games (the right unit for a service), Players counts people (the right unit for a funnel). Don't merge them, and don't "fix" `FinishRate` into a funnel.
  2. **Two numbers per rung.** The bar is share of arrivals (how much of the original crowd is left); the legend is share of the step *above* (how well that one hand-off worked). With only the first, a step that inherited a small crowd is indistinguishable from a broken one — and it's what stops the always-full top bar from being the wasted row that kept a funnel off this dashboard in the first place.
  3. **"Played again" is ordered against the earlier finish**, not just "started two rounds": the day's last `started_at` must beat its first completion. Two boards opened in two tabs before either was played is not somebody coming back for seconds. It's a floor — finish, replay, finish again still counts once.
  4. **The scope toggle is device-days, clipped to measured days.** One day here is tens of people, so it defaults to the pooled window; a device that played on three days counts three times, because "of the people who showed up, how many played" is asked afresh each day. The window starts at `visits.since` — pooling earlier days would keep their plays and drop their (unmeasured) arrivals, flattering the top exactly as much as it understated the bounce. Before the beacon, the arrivals rung is **omitted**, never drawn as 0.
  5. **The headline ranks fall-offs by count, not by rate** — a 60% loss at the bottom is four people, a 25% one at the top is thirty, and it's the thirty that are worth a morning. Step conversions carry `RangeHint` like every other thin rate on this dashboard, and the played→finished drop reuses the `DNF_GRACE_MINUTES` split so a live afternoon reads as people still eating.
  6. **Event palette, not a fifth colour system**: start = teal, complete = cherry, share = mustard; arrivals take muted ink because they're the one rung that isn't an event, and "played again" is teal because it *is* another start.
- **My own test data** (admin **Activity** tab, under the feed): the admin is also a player, and at tens of rounds a day one person play-testing is a visible fraction of every rate on the dashboard — so "This device's data" reviews what this browser has recorded and then deletes it. `GET /api/admin/device-data?player=<id>` is the review (counts only, folded pure in `worker/device.ts` — `foldDeviceData`, unit-tested in device.test.ts), `DELETE` on the same path is the wipe; `MyDataPanel` in ActivityPanel.tsx renders both. Five things are load-bearing:
  1. **"Me" is the Activity feed's `mine` filter, unchanged** — the anonymous localStorage `player_id` via `peekPlayerId()`. Same identity for both, so reviewing the rows above and deleting them below can't describe different sets. It follows that this is **per-browser, not per-person**: your phone and the Discord Activity (separate origin, separate id) are somebody else, which the panel says out loud.
  2. **The review is a step, not a suggestion.** The delete button doesn't exist until the summary has loaded — prod D1 has no automatic backup, so an irreversible wipe must not be reachable without having been shown what it covers. "Show these rows" hands the actual review to the feed set to "Only mine"; the panel answers only the part the feed can't, which is *how much*.
  3. **Three tables, named separately** — `analytics_rounds`, `analytics_visits` (arrivals), `announcement_views` (reach). Arrivals are the reason this exists: opening the game and never guessing writes a visit row *and nothing else*, so a morning of reloading the page to check a change is invisible in the round counts and reads as pure bounce in the funnel. `dish_requests` is deliberately **not** included — a suggestion isn't analytics, and the Requests tab already removes them.
  4. **The delete reports what each table actually lost**, not what was asked for: a wipe that matched nothing is a wrong id, and echoing the request would hide that. Counts are folded from a `GROUP BY (kind, surface)`, zero-filled over the enums, and a value outside them still counts toward `total` — `total` is what the delete removes, so it's the number that has to be right.
  5. **The device id survives the wipe.** Nothing touches localStorage, so the next round played here records under the same id and clears the same way. Minting a fresh id would scatter your testing across ids the `mine` filter no longer recognises.
- **Beacon paths are blocker-bait — keep them boring.** The engagement beacons POST to `/api/rounds/seated|start|complete|share` (mounted in worker/index.ts; the handler file is still `worker/routes/analytics.ts`), and the admin feed reads `/api/admin/recent-rounds`. They were originally `/api/analytics/*` and `/api/admin/analytics/events`, which ad blockers match by pattern — the admin one failed loudly (a bare `NetworkError`, nothing in the Worker logs), but the **player beacons failed silently**: they're fire-and-forget, so a blocked beacon is indistinguishable from a delivered one and those players simply never appeared in any count. Don't reintroduce `analytics`, `event`, `track`, `collect`, `beacon`, `telemetry`, `pixel`, `visit`, `view`, or `pageview` into a client-called URL — the last three are why the arrival beacon is `/seated` rather than the obvious name. (`/api/stats` is fine — shields.io fetches it server-side, no browser involved.)
- **Announcements** (notices posted to players): written in the admin **Announcements** tab (`src/admin/AnnouncementsPanel.tsx`), shown as a modal on **Today's Special only** — never on a Leftover, Chef's Choice, preview or `?special=` playtest, which are side doors. Ordering is deliberate: a first-timer gets the how-to, *then* eligible notices; the auto-opened check for an already-finished round also goes first. Multiple live notices **queue** (oldest `start_date` first, one card at a time).

Don't "improve" this into an HTML renderer.

Two constraints if you retune it: the exit must stay within `MODAL_EXIT_MS` (components.tsx) or the fallback unmount timer cuts it, and the footer's stagger is **transform-only** (`footer-rise`) because it holds the card's only button — a delayed `both`-filled opacity would leave it invisible for as long as the animation stalls.
  - Paths are `/api/announcements` + `/api/announcements/seen`, which dodge the blocker-bait words (see the beacon note below). Both failure modes are visible rather than silent — a blocked GET means no notice appears, a blocked POST shows as reach far under the day's player count.

## Adding dishes (when asked)

The user will say things like **"add dishes: Pho (Vietnam), Bibimbap (South Korea), Empanadas (Argentina)"**. Minimum they must give per dish is the **name** (country helps). I infer the rest (region/course/temperature/protein/ingredients/5 clues) from the dish — but **ask, don't guess, when a field is genuinely ambiguous** (e.g. regional protein variants). If they want full control they can specify any field explicitly.

**One dish = one `dishes` row + exactly 5 `clues` rows.** A dish is only schedulable with **≥3 ingredients AND exactly 5 clues** — always produce both.

### Per-dish fields (all NOT NULL; enums CHECK-enforced in migrations/0001_init.sql)

| Field | Rule |
|---|---|
| `name` | Display name, **unique**. Double apostrophes in SQL (`Shepherd''s Pie`) |
| `slug` | lowercase-kebab of name, **unique**, ASCII — strip accents (`Crème Brûlée` → `creme-brulee`) |
| `country` | Real country, free text (`Italy`, `United Kingdom`, `Türkiye`) |
| `region` | Exactly one of: `north-america` `latin-america` `europe` `middle-east` `africa` `south-asia` `east-asia` `southeast-asia` `oceania`. Drives the yellow "near" country match — bucket the country correctly |
| `course` | `breakfast` \| `appetizer` \| `entree` \| `dessert` \| `drink` |
| `temperature` | `hot` \| `cold` (as served) |
| `protein` | `beef` \| `pork` \| `poultry` \| `seafood` \| `lamb` \| `vegetarian`. Pick the dominant one; `vegetarian` if none |
| `ingredients` | JSON array, **canonical lowercase singular**, **≥3** (aim 5–8). Reuse existing pantry spellings — `tomato` not `tomatoes`, `bell pepper`, `olive oil`. Grep seed.sql for an ingredient before coining a new spelling |

### The 5 clues (`order_index` 1→5, revealed after each miss — never name the dish)

1. Broad geography/region hint ("comes from Europe — a country shaped like a boot")
2. Origin / history
3. Fame / pop-culture moment
4. Key ingredient or technique
5. Near-giveaway (everything but the name)

### Where the rows go

- **Append to `seed/seed.sql`** (the canonical catalog): next sequential dish `id`, same `INSERT INTO dishes (...) VALUES` format, and 5 clue rows in the `INSERT INTO clues` block. Keep it the source of truth.
- **Also add an additive migration** `migrations/000N_add_<batch>.sql` to ship them to the LIVE DB — INSERTs only, **no `DELETE`s**, dish **keyed by slug** not a hardcoded id (`(SELECT id FROM dishes WHERE slug='…')` for clue `dish_id`). Never re-run the seed against prod (it wipes admin edits); CI applies the migration on the next `v*` release.
- **If the user says the dishes are fan/player submissions**, tag them: `UPDATE dishes SET is_fan_submission = 1 WHERE slug IN (…)` in both the seed and the migration, keyed by slug (never a hardcoded id). Leave the `INSERT INTO dishes` column lists alone — the column defaults to 0.
- **Pool only — never touch the `schedule` table.** New dishes land in the active pool (`is_active` defaults to 1); leave assigning them to dates to the `/admin` auto-fill (least-recently-served, skips dishes used in the last 60 days). Don't add `INSERT INTO schedule` rows.
- Finish with `npm test && npm run check`; verify each new dish has 5 clues + ≥3 ingredients before committing.

## Conventions / gotchas

- Ingredients: JSON TEXT column, canonical lowercase singular ("tomato" not "tomatoes"). Admin tag input autocompletes from existing vocabulary — reuse names, don't fork spellings
- Dish is "schedulable" only with ≥3 ingredients AND exactly 5 clues (enforced in PUT /schedule + shown in UI)
- Schedule: past dates locked; DELETE dish blocked while scheduled today/future; autofill = least-recently-served, skips dishes used in last 60 days
- Regions enum (near-match buckets): north-america, latin-america, europe, middle-east, africa, south-asia, east-asia, southeast-asia, oceania. Courses: breakfast, appetizer, entree, dessert, drink. Proteins: beef, pork, poultry, seafood, lamb, vegetarian
- SQL in seed files: escape apostrophes as `''`
- vitest.config.ts exists SEPARATELY from vite.config.ts on purpose (tests must not load the cloudflare plugin). Its `include` covers `worker/` **and** `shared/` — the pure folds all live in one of those two
- `tsc -b` is incremental and will happily report success on a stale build graph — use `npx tsc -b --force` when you've changed a type in `shared/` and want to trust the answer
- tsconfig is 3 composite projects; worker code must not use DOM libs; app code gets DOM. Shared/ is included by both
- `worker-configuration.d.ts` is generated (gitignored) — run cf-typegen, never hand-edit; Env type comes from it
- Cookies: HttpOnly+Secure+SameSite=Strict, 7-day HMAC token ("session" payload). Password check is digest-compared (timing-safe-ish)
- Don't add npm deps casually — the only runtime deps are hono, react, react-dom
- Windows repo (CRLF warnings from git are noise; ignore)
- Changing art: swap ai-*.svg in place (same viewBox ratio), update ASSETS.md; the neon logo is CSS text, not an image

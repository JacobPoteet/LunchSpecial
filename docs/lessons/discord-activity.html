Part 01

No second build

Lunch Special runs as a Discord Activity, which means a player can launch it from a voice channel and play inside a Discord window. There is no Discord version of the app. npm run deploy ships the public site, and the Activity comes along with it.

Discord does not host the code. You register a URL mapping in the developer portal, pointing / at lunchspecial.app, and Discord frames the live site through its own proxy. Whatever you deployed this morning is what a player sees in the channel this afternoon.

That arrangement works because of properties the app already had, none of which were added for Discord:

  • Every client call is a relative /api/* path, so the proxy carries them without a rewrite rule.
  • Fonts, art and assets come from the Worker, so nothing needs a CDN allowance in Discord's content policy.
  • The whole thing is same-origin, so no CORS negotiation happens at all.

An app that pulled fonts from Google and its API from a second domain would need proxy configuration for each one. The reward for keeping a small app self-contained arrives years later, in a feature nobody had planned.

The Discord-specific code fits in one directory:

FileOwns
src/discord/bootstrap.tsDetection, the SDK handshake, sticky parameters, portrait lock
src/discord/auth.tsThe single authorization and the token it yields
src/discord/presence.tsRate-limited pushes of the profile line

Part 02

Detection, and the race at boot

Discord appends frame_id to the iframe URL. Its presence is the whole detection mechanism, and it is the same signal the SDK uses internally.

export function isDiscordActivity(): boolean {
  return new URLSearchParams(window.location.search).has("frame_id");
}

On the open web that parameter is absent, initDiscord() returns null, and the Embedded App SDK never downloads. The import is dynamic for exactly that reason, so a static import cannot drag the SDK into the bundle a web visitor parses.

main.tsx awaits initDiscord() before mounting React, which creates a problem: sdk.ready() waits on Discord's RPC parent, and a slow or broken handshake would leave the player looking at an empty iframe. So the boot races the handshake against a five second timer, and mounts either way.

The bug this shape exists to prevent

The five feature registrations used to sit on the winning branch of the race. On a fast connection everything worked. On a slow Activity start the timer won, React mounted, the handshake landed a second later, and the share button did nothing for the rest of the session, with no error anywhere. The registrations now sit inside the handshake's own .then(), so a handshake that arrives at 5.1 seconds still delivers a working SDK.

A missing VITE_DISCORD_CLIENT_ID logs an explicit console error rather than failing at the first SDK call. The variable is public and build-time, so it ships in the bundle. It belongs in .env.local and in a repository Actions variable, never in .dev.vars alongside the secrets.

Part 03

The parameters that keep falling off

The game ships no router. Switching modes navigates by assigning a new URL, which wipes the query string. Inside Discord that means the first board carries frame_id and every board after it does not.

The symptom showed up in the analytics rather than in the game: Chef's Choice and Leftovers rounds played inside Discord were recording as web plays. The fix captures Discord's parameters into sessionStorage on the first load of the tab, then re-attaches them to any URL the app navigates to.

/**
 * Rewrite an in-app URL so it keeps the player on the same surface: inside
 * Discord it re-attaches the Activity params the assignment would otherwise
 * drop (params already on `url` win). A no-op on the open web.
 */
export function surfaceUrl(url: string): string {
  if (discordParams === "") return url;
  const [path, query] = url.split("?");
  const merged = new URLSearchParams(discordParams);
  if (query) for (const [key, value] of new URLSearchParams(query)) merged.set(key, value);
  return `${path}?${merged.toString()}`;
}

Nine parameters get preserved: frame_id, instance_id, platform, channel_id, guild_id, location_id, custom_id, referrer_id and mobile_app_version. The SDK reads several of them back out of the URL, so all nine have to survive.

isDiscordActivity() stays strictly URL-based, since the SDK handshake needs the real parameters on this page load. currentSurface() reads the sticky copy, because a beacon fired an hour into a session still needs to know where it is. Two questions that look identical and take different sources.

The arrival-source capture in the analytics pipeline hit the same wall and took the same shape. Its module comment points at this one so the next person finds a pattern rather than a coincidence.

Part 04

One authorization, two scopes

Rich Presence needs the rpc.activities.write scope, so the Activity has to run an OAuth flow. That flow is the only moment this anonymous game touches a real identity, and every rule around it exists to keep the touch as small as possible.

Two scopes, measured

The list is identify plus rpc.activities.write. The second grants setActivity. The first is required by the SDK's authenticate() hop, which parses Discord's reply against a schema where the user object is required. A token that cannot produce one fails the parse, and every later setActivity with it.

That was established by experiment rather than by reading:

/**
 * **This was measured, not reasoned** (GitHub #101 → #106). The list was
 * deliberately cut back to `rpc.activities.write` alone, with `type: 0` left in
 * so the two candidate causes were separated, and presence went silent again.
 * Both scopes: works. One: dead. The cost of `identify` — username, avatar and
 * banner on the consent sheet of a game that has no accounts — is real enough to
 * be worth one round trip to confirm we were paying it for a reason. We were.
 * Don't spend a third: leave this list alone.
 */

Two candidate causes, one variable changed at a time, and a note in the code so nobody repeats the test. The consent sheet lists what a scope grants, so on a game with no accounts each additional scope is a real cost paid by the player.

The identity gets dropped

Taking identify means the app receives a user object. It never reads it. The object is not stored, not sent to the Worker, and not written to localStorage. The game stays anonymous, with per-device state and no identity in any table.

Once per page load, whatever happens

The call uses prompt: "none", so a returning player sees nothing. A refusal or a broken exchange sets an unavailable flag that is never retried, because a consent sheet appearing over a live board costs more than the missing presence line is worth.

Two accessors express the policy. ensureAuthorized() starts the flow and caches the promise. peekToken() returns the token if it exists and never triggers anything. Presence calls the first, so authorization happens on the first real board. The share button calls the second, so pressing share can never be the thing that raises a prompt.

Part 05

The hop through our own server

Discord's SDK hands the client an authorization code. Turning it into an access token requires the app's client secret, which must never reach a browser. The Worker performs that exchange, and returns one field.

// Only the token goes back — not the refresh token, scope echo or expiry,
// none of which the Activity's `authenticate()` call has any use for.
return c.json({ accessToken });

Four endpoints live on the Worker, and three of them share a contract: a deployment without Discord secrets answers 503 and runs the entire game without them.

EndpointDoesStores
POST /api/discord/tokenExchanges the code for an access tokenNothing
POST /api/discord/attachmentForwards the score card to Discord's CDNNothing
POST /api/discord/interactionsAnswers Discord's signed callbacksA handle and a token, for 15 minutes
POST /api/discord/progressPatches the live messageNothing

Both outbound calls log the response status and never the body, because a Discord error envelope can echo back the submitted code or the bearer token. The attachment route bounds the upload twice, once on the declared Content-Length and once on the blob it actually received, so a bad client cannot make the Worker hold an arbitrary payload in memory on its way to Discord.

The attachment route also carries no credentials of its own. It forwards the player's bearer, which is what makes the resulting attachment theirs to share.

Part 06

Presence: two lines that must never name the dish

While someone plays, their Discord profile can show two lines under "Playing Lunch Special": which mode they are in, and how far through the six guesses they have got.

A profile is read by people who have not played today. Naming the dish would hand them the answer, which makes this a spoiler surface rather than a decoration. The copy is a pure fold in shared/presence.ts, and its test asserts that the fold's whole output space stays inside a character class no dish name can survive.

The rule

A guess count says nothing about the dish, so progress is safe to publish. The answer, the guessed dishes and the clue text are not. The same rule governs the score card, and it is why the public API never leaks the target except through /reveal.

The client half owns one thing: the rate at which updates leave. Discord allows five SET_ACTIVITY calls per twenty seconds, so the module pushes at most one every four seconds. A round cannot change state that fast, but React effects can re-run, and a burst that trips the limit would drop the interesting update rather than the noise.

The throttle sends a trailing update instead of dropping one:

// A trailing update, not a dropped one: whatever `desired` holds when the
// timer fires is what gets sent, so the newest state always wins.
if (timer === null) {
  timer = setTimeout(() => { timer = null; flush(); }, wait);
}

A failed push clears the cached payload rather than latching it as sent, so the next state change retries the same content instead of skipping it.

One honesty detail sits in the fold. Discord can show an elapsed timer, and the presence carries a start time only while a round is live. A board restored from localStorage gets none, because that round began on a page load nobody has any record of, and a timer counting from the restore would measure the wrong thing.

Part 07

The live progress message

On the player's first guess, the app posts one message into the channel they launched from: their name, their face, a picture of the board, and a Play now! button. Every guess after that edits the same message. The round ending flips its text to the past tense.

A whole round costs the channel one message rather than six, and anyone scrolling past sees a game in progress with a one-click way into their own.

Why the message is created by Discord

The client cannot post into a channel, and should not be able to. Instead it calls shareInteraction, which asks Discord to invoke the app's own registered command. Discord then sends a signed interaction to the Worker, and the Worker's reply becomes the message.

The player's name and face arrive on that signed payload. A player cannot make the app announce somebody else, because the only identity in the flow is the one Discord vouched for.

Why the edits never re-send embeds

Discord replaces embeds wholesale on a patch. Keeping the author line means writing it once at creation and never touching it again, so the edit sends content and attachments and nothing else. That decision is what keeps the database table down to three columns:

CREATE TABLE IF NOT EXISTS discord_messages (
  handle            TEXT PRIMARY KEY,
  interaction_token TEXT NOT NULL,
  created_at        TEXT NOT NULL DEFAULT (datetime('now'))
);

No user id, no username, no avatar, no channel, no guild, no image. Read that table cold and it tells you nothing about anybody: a random handle, a credential Discord kills after 15 minutes, and a timestamp. Putting the name in content instead of the embed would force the app to store it.

The handle

Sixteen bytes of hex, minted in the browser, meaningless anywhere else. Not the user id and not the channel id. Rows get swept by age on write, because they expire on Discord's clock rather than ours and there is no state worth a scheduled job.

Verify the signature or answer nothing

The interactions endpoint is a public URL that posts messages into people's servers as this app. One check stands between those two facts, and it runs against the raw request body:

// The RAW body: Discord signs the exact bytes it sent, so re-serializing the
// parsed object would change the signed message and fail every request.
const body = await c.req.text();

Re-serializing parsed JSON changes key order, whitespace and number formatting, and every request fails. The verifier never throws: a malformed header, a wrong-length key and a runtime without Ed25519 all return false, which is the same answer as a forgery.

Discord validates a newly-saved endpoint by sending a deliberately bad signature and requiring a 401. A 401 during setup means the check works.

The avatar nobody stores

worker/avatar.ts builds a URL and hands it to Discord, which fetches the picture itself. No avatar bytes pass through the app. Two details in that small file earn their tests: an animated avatar hash starts a_ and has to be requested as a GIF, and a user with no avatar gets a stock face indexed by (id >> 22) % 6 in BigInt. Doing that shift in Number rounds the snowflake and lands everyone on the same one or two faces.

Trailing, not queued

The client sends one update at a time and keeps only the newest pending state. Three guesses landing during an upload should show the third, since the message displays a position and only the latest one is true.

A 410 from the Worker means Discord expired the token, which is the ordinary end of a long round. The loop retires without a word.

Part 08

Posting the check to the channel

On the web, sharing a finished round copies text or opens the share sheet. Inside the Activity it used to mean copying text and asking the player to go and paste it: leave the game, find the message box, paste. Three steps on the one action a daily puzzle spreads by.

The native path replaces those with a dialog, in three hops:

  1. Draw the card as a PNG, from a pure fold in shared/scorecard.ts rendered by a canvas module that loads dynamically.
  2. Upload it through the Worker to Discord's attachment endpoint.
  3. Open the dialog with openShareMomentDialog({ mediaUrl }).

The dialog takes a Discord CDN URL and nothing else, which is why the result travels as a picture rather than as the emoji grid.

Two details in the drawing keep the image alive longer than the code around it. Tiles are drawn as rectangles rather than emoji, and the palette is hard-coded from base.css instead of read at draw time. A card posted last month should not change when the stylesheet does.

The safety argument

shareToChannel() never throws and returns a boolean. On false the caller copies the text instead, which is what Discord players had before this existed. Trying and failing is never worse than not trying, and that property is the entire reason the feature is allowed to be this complicated.

The clipboard fallback has its own wrinkle. navigator.clipboard sits behind a permissions policy Discord's iframe does not grant, so the modern API alone rejects there. copyShareText() falls back to a hidden textarea and document.execCommand("copy"), returns a boolean, and the button shows a retry label on false.

One thing the return value deliberately does not distinguish: a player who opens the dialog and closes it without posting counts as a success. They were offered the choice, and stuffing their clipboard after they declined would second-guess an answer they already gave.

Part 09

The room the game is in

Three small features make the Activity feel like an Activity. None takes an OAuth scope, and all three are no-ops on the open web.

The invite button

It appears in the check's footer, and hides when sdk.guildId is null, since DMs have nothing to invite anyone to. The documented approach checks CREATE_INSTANT_INVITE first, which costs a guilds.members.read scope. The code calls the dialog and swallows the refusal instead. Being wrong produces a dialog that does not open, which is what the check would have produced anyway, for the price of a third line on the consent sheet.

"3 others are at the counter"

Discord reports who is connected to this Activity instance, and the payload carries usernames, avatars and nicknames. One number leaves the module:

/**
 * **The count is all that ever leaves this module.** Discord's payload carries
 * full user objects — usernames, avatars, nicknames — and reading any of them
 * would put identity into a game that deliberately has none. `.length` says the
 * diner is busy without saying who's in it.
 */

You get subtracted from the count, and the bar hides at zero.

Picture-in-picture

Discord can draw the Activity as a small floating tile. The layout mode gets stamped onto <html data-discord-layout="pip"> and the stylesheet does the rest: the marquee, the header, the clue tickets and the footer all disappear, and the blurred diner backdrop goes with them, since two fixed full-viewport layers with a blur filter is the most expensive thing on the page and none of it is visible behind a card that now covers the tile.

An attribute rather than React state, because picture-in-picture is a property of the window rather than of the round, and a player can flip it back a second later. Scoped to the attribute rather than to a width query, because a floating tile and a narrow phone share a width and share nothing else.

Mobile clients also get a portrait lock on handshake. The board is a portrait menu card laid out for 375 pixels; rotating a phone hands it a viewport a few hundred pixels tall, where the check barely fits. Every other surface lets the player choose that. The Activity is the one place the app can decline.

Part 10

Failing in silence, on purpose

One sentence governs every module in this directory: a round must play identically whether or not any of this works. The code enforces it in four ways.

PatternWhereEffect
Nothing is awaited by the gamePresence, progress, socialA hung Discord call cannot stall a guess
Nothing throwsShare, progress, inviteThe caller gets false and takes the other path
Failure is stickyProgress, authorizationOne failure retires the loop rather than retrying into a rate limit
503 for unconfiguredThree Worker routesA deployment with no Discord secrets runs the whole game

Silent failure creates its own problem: this flow only reproduces inside the real Discord client, where "the share button did nothing" is unbisectable. So each multi-hop function tracks which hop it is on and names that hop in the warning.

let step = "draw";
try {
  // ... draw the card
  step = "upload";
  // ... POST to /api/discord/attachment
  step = "share dialog";
  // ... openShareMomentDialog
} catch (err) {
  console.warn(`[discord] native share unavailable (failed at: ${step}) — falling back to the clipboard:`, err);
  return false;
}

Three words in a console line turn an unreproducible bug report into a bisected one.

Two more constraints hold across the surface. Preview and playtest modes publish nothing, gated on the same tracked flag the analytics beacons use, because an admin rehearsing tomorrow's board is nobody's round and has no business in a channel. And a board restored from localStorage publishes on mount, which is why resetProgress() is declared above the publisher in GamePage: effects fire in order, and resetting afterwards would orphan that first post.

The footer's side pages stay plain same-origin links with no target="_blank". They navigate the iframe, Discord's proxy serves them, and each carries its own way back to the diner. openExternalLink was tried and does not apply, because the game has no outbound links at all.

Part 11

What transfers to your next embed

  1. Stay self-contained and the embed comes free. Relative API paths, self-hosted assets and one origin cost nothing on the open web and remove every proxy question inside somebody else's client.
  2. Separate "when do I render" from "when do I have the SDK". Racing a handshake to protect the mount is right. Attaching features to the race's winner is how a feature dies in silence.
  3. Ask for the fewest scopes, and prove the number. Cut one, watch what breaks, write down the result next to the list.
  4. Let the platform hold the identity. Reading the name off a signed payload, writing it once and never re-sending it is what keeps a table down to three anonymous columns.
  5. Name the hop in the log line. Any flow you cannot reproduce locally needs to say where it stopped.
  6. Give every optional feature a fallback that already works. The clipboard is what the native share is allowed to fail into, which is why the native share is allowed to exist.

The measurement side of the same surface is covered in Analytics Beacon Pipeline, and the panels reading it in Admin Analytics Dashboard.

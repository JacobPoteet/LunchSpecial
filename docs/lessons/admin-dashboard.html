Part 01

The constraint: small numbers

Most dashboard advice assumes you have plenty of data. Lunch Special has tens of rounds a day. At that volume a percentage is a fragile object: one more player losing swings a win rate by ten points, and yesterday's dip and yesterday's noise look the same on a chart.

That single fact shapes the whole design. A big-number dashboard can get away with drawing whatever the query returns, because volume smooths the lies out. A small-number dashboard that does the same thing will show you a figure that went up, and you will ship something on the strength of it.

So the admin UI spends most of its complexity on one job: making sure you can tell a measurement from a mood. The comment at the top of the Experiments tab states the design brief for the entire dashboard.

/**
 * The tab the rest of the dashboard exists to serve.
 *
 * Every other panel answers "what is happening". This one answers "did the thing
 * I shipped do anything", which is the question the game is actually run on ...
 *
 * The design constraint is that at tens of rounds a day, the honest answer is
 * usually **"not yet"**. A dashboard that can't say that will instead show a
 * number that went up, and its owner will ship on it. So "inconclusive" is a
 * first-class verdict here, it comes with how many more days would settle it, and
 * the noise a difference has to beat is printed next to the difference.
 */

Everything below follows from that. Six tabs, four colour meanings, five separate minimum-sample thresholds and a refusal to draw a bar for something nobody measured yet.

Part 02

One question per tab

The dashboard started as one scroll about nine screens long. Splitting it into tabs was the obvious fix, and the first split got it wrong in a way worth studying: the tabs were organised by data source. Overview and Players both rendered the day slice. Trends carried the retention ladder and the country pie, on the grounds that both are charts with an x-axis.

A tab defined by "has an x-axis" is not a question anyone asks. The second arrangement gives each tab one question, and moves panels wherever the answer lives.

TabThe questionWhat sits there
TodayWhat is happening right now?Today's Special, tomorrow's booking, pace against recent days, finish rate, last order
MenuWhat are we serving, and how does it land?Per-dish performance first, then the catalogue mix
PlayersWho is playing?New against returning, the drop-off funnel, repeat visits, countries, arrival sources
TrendsWhere is it all going?Time and nothing else: all-time growth, a 30-day spark, weekday profile, hour heatmap
ExperimentsDid anything I did cause any of it?The change log, with a verdict per change
ActivityWhat actually happened?The raw feed, grouped into visits

Read left to right and the order is a narrative: the day, the food, the people, the direction, your own decisions, the receipts. Experiments sits second from the end on purpose, because you arrive there having already watched a number move.

The reorganisation rule

When two tabs both hold part of an answer, neither tab answers anything. The retention ladder and the country pie moved to Players so that Trends could become a tab about time and nothing else. One question, asked at four scales: the whole run, the last month, the week, the day.

Two smaller decisions keep the tabs usable. The current tab writes itself into the query string with history.replaceState, so a reload lands where you were without stacking history entries. And leaving the dashboard for the dish list clears ?tab= on unmount, so the parameter never outlives the thing it describes.

Part 03

How a panel is assembled

The data path has three stages, and the boundaries between them are strict. A route runs the SQL. A pure module folds rows into a shape. A React component renders that shape and computes nothing.

Two pieces of state live above the tabs so they survive switching between them: the surface filter (web, Discord or both) and the picked day. The day defaults to null rather than to today's date, which sounds like a detail and prevents a real bug. A pinned date goes stale at midnight ET. A null keeps following the rollover.

The wording lives above the tabs too. analyticsUi.tsx holds the pieces more than one tab needs, and the reason is stated in the file: the difficulty sentence appears on both Today and Players, so the two can't drift into describing the same number differently. A shared constant is cheaper than two panels that disagree about what a figure means.

Part 04

Count the right unit, then name it

Three units run through this data: a round (one game), a device (one browser), a visit (one device on one day). Mixing them produces charts where every number is correct and the picture is false.

The finish-rate panel on the Today tab switches units halfway down, and says so in both rows:

// The top row counts **people**, the rows under it count **games**, and that
// switch is not sloppiness — it's the only way the arithmetic is true. A visit
// is one device per day, while `started` counts rounds, so a player who does
// the Special and three Leftovers is one arrival and four starts: dividing
// those would report a 400% play rate. So the funnel's first question is "of
// the people who showed up, how many played", and only then does it switch to
// games. Both rows name their own unit so the change is legible.

The player funnel on the next tab counts devices at every stage, which makes each bar a genuine subset of the one above it. That is the only condition under which a bar's width carries meaning. The finish-rate panel counts games, because a service is measured in covers rather than in regulars. Both live on the dashboard and neither one gets "fixed" into the other.

Worth stealing

Write the unit into the label, every time. "Devices" and "games" are four keystrokes apiece, and they are what stops somebody dividing one by the other six months from now.

One more unit trap sits in the funnel, and the fix is instructive. A later stage can legitimately outrun an earlier one, because start, complete and share arrive as independent beacons. A share whose completion beacon never landed is a real player the row above cannot see. The code clamps the bar and leaves the number alone:

// The *bar* is clamped, the percentage beside it is not. A rung can
// legitimately outrun the one above ... Clamping the number would
// hide that; clamping only the fill keeps the shape readable.
const width = Math.min(100, Math.max(0, (s.n / top) * 100));

Part 05

Tracks instead of funnels

A funnel chart wastes its first row. The top bar is full width by definition, so it carries no value, and every bar below it gets read against a baseline nobody drew. That works when the stages share a denominator. Two of this dashboard's charts do not.

The finish-rate panel and the repeat-visit ladder both draw tracks: each row is its own denominator, drawn as an empty rail, with the answer as a fill inside it.

The remainder gets the same treatment. An earlier version reported every unfinished round as a walkout and clamped the count at zero, which on a live afternoon reads a full diner as a mass exit. Start and complete arrive as separate beacons, so the split cannot come from the rows. It comes from the age of each start cohort: DNF_GRACE_MINUTES is two hours, and a round begun inside that window counts as still playing. Both halves get named. Neither gets inferred in silence.

The retention ladder keeps its cohort sizes as text rather than as bar width, for a reason worth borrowing: encoding it as bar width too would spend the axis on a number already written twice. A reader can hold "17 of 50". Making the bar shorter as well says the same thing twice and costs you the ability to compare rates down the ladder.

Part 06

Four colour meanings, all spoken for

The game's palette gives the dashboard three hues to work with. Four meanings already claim them, and adding a fifth means retiring one first.

PaletteEncodesWhere you see it
mustard / teal / cherry game kind Today's Special, Leftovers, Chef's Choice, on every stacked bar
start / complete / share event type Activity feed pips, finish-rate fills, funnel rungs
single-hue teal ramp rank The country pie, ordered by share, with the tail pooled in grey
dashed ink an annotation over data The constant-pace line through the growth curve

The same three hues carry the first two meanings in different orders, which sounds like a collision waiting to happen. It holds because the two never share a chart. A stacked bar is always about game modes. A fill inside a track is always about events. The stylesheet says so at each site:

/* Fills use the Activity feed's EVENT colours (complete =
   cherry, share = mustard), never the kind palette, which means game mode. */

Two refusals matter as much as the assignments. The country pie takes one hue at varying strength rather than a categorical set, because a categorical set would be a fourth meaning on borrowed colours. And no colour is ever assigned to a player. Following one device through the Activity feed is an action: you click a chip and everything else dims. A per-device palette would collide with all three existing meanings at once.

Menu-mix bars stay one hue for a different reason. Nine region colours would re-encode what bar length already tells you.

Part 07

Uncertainty, drawn selectively

Every rate in the app passes through shared/sample.ts, which returns the percentage together with a 95% Wilson interval and the denominator it came from. The interval reaches the screen only when the denominator falls under SMALL_SAMPLE_MIN, which is 30.

/**
 * The honest range around a rate — but only when the sample is thin enough that
 * the point estimate can't carry itself.
 *
 * Rendered selectively on purpose. An interval on every number on the page
 * teaches you to stop reading them; an interval on exactly the numbers that need
 * one is a signal about which numbers those are.
 */
export function RangeHint({ n, of }: { n: number; of: number }) {
  const label = rangeLabel(rate(n, of));
  if (label === null) return null;
  return <span className="rate-range" title={SAMPLE_NOTE}>{label}</span>;
}

The selectivity is the design. Error bars on everything become wallpaper inside a week. Error bars on four numbers out of forty tell you which four to distrust, before you have read any of them.

Wilson rather than the textbook normal approximation, because this game sits where the approximation breaks: small samples and rates pinned near zero or one. Almost nobody shares. Almost everybody solves. The normal approximation hands back a zero-width interval at four wins out of four, which is the most confident-looking output a wrong method can produce.

One wording for the caveat lives in one constant, and every range on the dashboard hangs it off the same tooltip:

export const SAMPLE_NOTE =
  `Under ${SMALL_SAMPLE_MIN} rounds the percentage moves several points on one player, so the range ` +
  `it plausibly sits in (95% confidence) is shown beside it.`;

Part 08

When a sentence is allowed to speak

Several panels open with a plain-English headline. "▲ 21% ahead of the last 7 days at this hour." "Aloo gobi is the toughest at 44% solved." Those sentences carry more weight than the table under them, so each one sits behind its own minimum sample.

ThresholdValueGuards
DIFFICULTY_MIN_SOLVES5"That Special played harder than average"
DISH_MIN_COMPLETED8A dish's win rate entering the hardest/kindest comparison
RETENTION_MIN_COHORT10"A first-timer comes back 38% of the time"
GROWTH_TREND_MIN_DAYS7The gaining / steady / stalling verdict
WEEKDAY_MIN_OCCURRENCES3Calling out a strongest or weakest weekday

The split between what a row may claim and what a sentence may claim is the part worth taking away. A row can quote one out of one, because it prints its denominator beside the percentage. A sentence cannot carry that denominator without turning into a paragraph, so the sentence stays silent.

/**
 * Null until **both** rungs clear RETENTION_MIN_COHORT ...
 * The rungs themselves can quote a thin cohort because each one prints its own
 * "1 of 1" denominator beside the percentage; a prose sentence can't carry that,
 * and "once they've come twice, 100%" off a single player is a claim the data
 * hasn't earned.
 */

Thin cohorts still appear. They get flagged in place rather than hidden, because "how many of my three-timers came back" is the whole question and a blank row answers it worse than a caveat does.

The pace sentence adds a second idea: compare like with like. "41 games started" at two in the afternoon means nothing on its own, so the panel compares the day's cumulative total through the current ET hour against the same hour across recent days. Below one game of baseline it returns null, because a percentage off a fraction is noise and an empty line beats a confident wrong number.

Part 09

"Too early to tell" is an answer

The Experiments tab keeps a log of deliberate changes: what shipped, when, and which metric it was meant to move. Naming the metric up front is the mechanism that stops you from shopping for a number afterwards, and reading a different one prints a warning.

Each entry gets one of four verdicts, and the fourth carries as much weight as the others:

VerdictMeans
▲ Moved upThe difference beat the noise
▼ Moved downSame, in the other direction
No detectable changeEnough data to say the change did little
Too early to tellNot enough data yet, with the number of days that would settle it

The last two are different claims and the dashboard keeps them apart. "No detectable change" is a finding. "Too early to tell" is a status, and it ships with daysNeeded attached so the tab tells you when to come back.

Counts and rates take different tests. A count gets a two-sample t against the pooled day-to-day spread. A rate gets non-overlapping Wilson intervals, through the same separated() helper the dish report uses before it calls anything the hardest dish on the menu. The sentence under each verdict names the bar the difference had to clear: the day-to-day swing for a count, the denominator for a rate.

The rule underneath

Rates pool over the period. A week's rate is that week's successes over that week's trials, never the average of seven daily percentages, or a one-round Tuesday outvotes a busy Saturday. The experiment series ships raw counts for the same reason: a pre-divided percentage cannot be re-pooled over a different window.

Part 10

Drawing the gaps

Analytics that grew one column at a time leaves holes, and each kind of hole gets its own treatment. None of them get drawn as zero.

Not measured yet

The visit beacon shipped long after the round beacons, so the arrival count is null for the game's early history. The finish-rate panel drops its top row on those days rather than drawing an empty rail, and one shared sentence explains why wherever a slice comes back null:

export function untrackedNote(trackingStart?: string | null): string {
  return trackingStart
    ? `Player tracking didn't start until ${trackingStart} — not measured before that, which isn't the same as zero.`
    : "Player tracking hasn't recorded anything yet.";
}

Has not happened yet

On today's hourly chart, the hours after the current one are drawn faded. An empty column at 9pm on a live evening and an empty column at 9pm on a finished day are different claims, and the faded state keeps them from looking identical. A past day passes null for the boundary, because every one of its hours is a real measurement.

Measured at one end only

A round needs both a start and a completion timestamp before the dashboard will quote a duration. Neither is ever filled in from updated_at. Those rounds light their pip and say "time not recorded". An abandoned round gets no duration at all, since now-minus-start measures how long ago something happened.

Measured, but implausible

Negative durations get dropped rather than clamped. The 15-minute play-time cap only ever reduces a figure, and the count of capped rounds rides along so the panel can state the trim out loud: the timer measures how long the tab was open, not how long anyone was playing. Solve times report a median and a p90 rather than a mean, because a round is a browser tab and some of them get left open until lunch.

Part 11

Nothing animates

admin.css declares no keyframes across 2,900 lines. That is a deliberate property, and it pays for itself twice.

The first payment is accessibility: a stylesheet with no animation needs no reduced-motion block, so there is nothing to forget to update when a new panel lands. The game's stylesheet has one and every keyframe goes into it in the same commit. The dashboard sidesteps the requirement by not creating it.

The second is legibility. The Today tab refetches every 30 seconds while you watch a service. Anything that moved on arrival would turn a quiet afternoon into a light show, and you would start reading motion as news. New rows arrive with a static rail that a timer removes.

The one thing to keep true

Introducing the first keyframe here also introduces the requirement for a reduced-motion block that has never existed. The cost of animation on this dashboard is not the animation.

Part 12

What transfers to your next dashboard

Seven of these rules have nothing to do with diners, games, or Cloudflare.

  1. Give each tab a question, not a data source. If two tabs hold half an answer, merge or move until one of them holds all of it.
  2. Name the unit in the label. Devices and games look alike in a number and behave nothing alike in a ratio.
  3. Draw tracks when denominators differ. Save the funnel for stages that share one, or spend a row on a bar that always reads 100%.
  4. Count your colour meanings before adding one. Four is a workable ceiling. Assigning a hue to an identity burns the budget fastest.
  5. Show uncertainty on the numbers that need it and nowhere else. Universal error bars are decoration.
  6. Let a row quote a thin sample; make a sentence earn it. The row prints its denominator, and a headline cannot.
  7. Ship "not yet" as a verdict, with a date attached. A dashboard that cannot say it will show you something that went up instead.

The pipeline that feeds all of this is covered in Analytics Beacon Pipeline, which ends where this document starts.

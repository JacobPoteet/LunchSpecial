Part 01

The problem: measuring a game with no accounts

Every analytics system answers the same question first: what is the thing I am counting? Lunch Special answers it under a hard constraint. There are no accounts, no logins, no email addresses, no user table. Nobody signs up. So there is no such thing as a "user" in this system, and pretending otherwise would be the first lie.

What exists instead are three countable units, and almost every argument in the rest of this document is really an argument about which of the three a given number should use.

UnitWhat it isIdentified byHonest name
Round One game board being played. Opened, guessed at, finished or abandoned. A random id minted when the board resolves "games"
Device One browser profile on one machine. Your phone and your laptop are two. A random UUID kept in localStorage "devices", loosely "players"
Visit One device showing up on one calendar day. Four boards in a morning is still one visit. The pair (day, device) "arrivals" or "visitors"

A device is not a person. Somebody who plays on their phone in the morning and their laptop at lunch is two devices forever, and there is no way to know that from inside this system. Somebody who clears their browser data becomes a brand new device with no history. Those are real limitations, not bugs, and the dashboard's job is to say "devices" where it means devices rather than quietly upgrading the word to "people".

The governing rule

Count the right unit, and name it. The player funnel counts devices at every stage. The finish-rate chart counts games. They sit on different tabs on purpose and are never merged, because a device that plays the Special plus three archive rounds is one arrival and four games, and stacking those two numbers in one chart makes the bars grow as they go down.

Everything the game knows is assembled from those three units plus a handful of tags, and all of it arrives by one mechanism: a small message the browser throws at the server and immediately forgets about. That message is a beacon.

Part 02

The five nouns everything is built from

Before the plumbing, the vocabulary. Five values ride on beacons, and every number on the dashboard is some combination of them. Where each one is minted matters enormously, because it determines who is allowed to lie about it.

1. player_id — the device

A random UUID generated in the browser the first time it is needed, then kept forever in localStorage under lunch-special:player.

// src/game/storage.ts
export function getPlayerId(): string {
  try {
    const existing = localStorage.getItem(PLAYER_KEY);
    if (existing) return existing;
    const id = crypto.randomUUID?.() ?? `${Date.now()}-${Math.random().toString(36).slice(2)}`;
    localStorage.setItem(PLAYER_KEY, id);
    return id;
  } catch {
    // Storage blocked (private mode) — an ephemeral id, so the beacon
    // still has a shape; it just won't survive the session.
    return `${Date.now()}-${Math.random().toString(36).slice(2)}`;
  }
}

Two details that look small and are not. First, it is generated lazily: the id does not exist until something needs it. Second, there is a sibling function, peekPlayerId(), which reads the id but never creates one. The admin dashboard uses the peek version, because merely opening the dashboard should not mint a device id that then appears in exactly zero rows of data. The mute button uses it too: reaching for the volume must not be the event that brings a device into existence.

2. round_id — the game

Also a random UUID, minted in the browser when a playable board resolves. Its entire job is to be the same string across three separate network requests, so that the "you started" message, the "you finished" message and the "you shared" message can be recognised as being about one game. It is stored alongside the round in localStorage, so a player who closes the tab mid-round and comes back tomorrow still completes the same round they started.

3. kind — which mode

One of three: daily (today's Special), leftover (an archive replay of an old puzzle) or random (Chef's Choice, a random dish). This is what stops a burst of archive replays from being read as a great day for the Special.

Two further modes exist and deliberately record nothing: admin preview and dev playtest. In the code they are excluded by a single boolean:

// src/game/GamePage.tsx
const tracked = !isPreview && !playtest;

Every beacon call site is gated on that one flag. It is why the admin dashboard links to a preview token rather than to the live game: an admin testing tomorrow's board must not move today's numbers.

4. surface — web or Discord

The game also runs embedded inside Discord as an Activity. Discord adds a frame_id query parameter to the iframe URL, and that parameter's presence is the whole detection mechanism.

A bug worth understanding

The game has no router. Switching modes navigates by assigning a fresh URL, which wipes the query string. So inside Discord, the first board logged as discord and every board after it logged as web, because frame_id was gone. The fix is to capture Discord's parameters into sessionStorage on the first load of the tab and re-attach them to every internal navigation. The arrival-source capture in the next item has exactly the same problem and is solved exactly the same way, on purpose.

5. source — where they came from

The utm_source on the landing URL: reddit, newsletter, and so on. Read once at module load, stashed in sessionStorage, and attached to the arrival beacon.

sessionStorage rather than localStorage is a deliberate and important choice. An arrival source describes this arrival. Persisting it would re-attribute every future visit from that browser to an ad clicked once, weeks ago, and a campaign would look like it was still working long after it stopped.

Two more values ride along that the client never sends at all — the country and the calendar day. Both are stamped by the server, for reasons covered in Part 06.

Part 03

What a beacon actually is

Strip away the vocabulary and a beacon is nine lines of code. This is the whole transport layer:

// src/api.ts
function beacon(path: string, body: unknown): void {
  try {
    void fetch(path, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(body),
      keepalive: true,
    }).catch(() => {});
  } catch {
    // analytics must never break the game
  }
}

Four properties are doing all the work here, and each one has consequences that show up hundreds of lines away.

It returns void

Not a promise. There is nothing to await, which means no call site can accidentally make a player wait on it. The guess flow submits the guess, updates the board, and throws a beacon over its shoulder on the way past.

It swallows every error, twice

The .catch(() => {}) handles a rejected request (offline, DNS failure, an ad blocker cancelling it). The outer try/catch handles the case where fetch itself throws before returning a promise. A failed beacon produces no console error, no retry, no user-visible anything. That is the correct behaviour for analytics and it is also the source of the single hardest problem in this whole system, which Part 05 is about.

keepalive: true

This is the flag that lets the request outlive the page. Without it, a browser cancels in-flight requests when the tab closes, and the "you finished the game" beacon fired half a second before someone closes the tab would frequently die in transit. With it, the browser promises to finish sending even if the document goes away.

It sends JSON in the body, not parameters in the URL

Partly hygiene, partly evasion. Content blockers match on URL shapes, and ?utm_source= in a request URL is a shape some of them strip. A stripped parameter would quietly relabel paid traffic as organic, which is worse than losing the request outright, because it is a wrong answer rather than a missing one.

Part 04

The seven beacons, one by one

Five of them are about rounds, two are not. Here they are as a set, then in detail.

PathFires whenCarriesWrites to
/api/rounds/seated A real playable board is ready device, surface, source analytics_visits
/api/rounds/start The first guess is submitted round, puzzle no., date, kind, surface, device, seed analytics_rounds
/api/rounds/complete The round ends, won or lost round, guess count, solved analytics_rounds
/api/rounds/share The share button succeeds round, puzzle no., date, kind, surface analytics_rounds
/api/rounds/sound The mute button is pressed device, surface, muted, toggle count sound_prefs
/api/announcements/seen A notice is displayed notice id, device, surface announcement_views

Seated: the top of the funnel

This one exists because of a gap. A round counts as "started" on the first submitted guess, which is the right definition — opening a page is not playing a game. But the cost of that definition is that everyone who loads the game and never guesses was completely invisible. The widest number the dashboard had was "games started", with nothing above it, so the most natural question anyone can ask about a change ("did it make more visitors actually play?") could not be asked at all. A change that doubled interest while halving conversion looked identical to no change.

So /seated fires on the board being ready. A guest is seated before they order. It carries only a device id, a surface and an arrival source, and notably no date: a visit belongs to the day it happened on, and the client has no authority over what day it is.

Start, complete and share: three messages, one row

These three share a round_id and progressively fill in the same database row. This is the single most important mechanic in the storage layer, so it gets its own diagram:

POST /start

On guess #1. Creates the row.

  • Sets kind, surface, country, device, dish
  • ON CONFLICT DO NOTHING
  • The only beacon that binds a device
POST /complete

On win or loss. Updates the row.

  • Sets guesses, solved, completed
  • Creates the row if start was lost
  • completed_at keeps the first value
POST /share

On a successful share. Updates the row.

  • Sets shared = 1
  • Re-sharing is harmless
  • shared_at keeps the first value

Notice the asymmetry in what each beacon is allowed to write. kind, surface, country and dish_id are insert-only: if the row already exists, a later beacon leaves them alone, because the /start that created the row already established them and a later message has no better information. The counters and flags are update-on-conflict. The timestamps are COALESCEd, so the first value wins and a replayed beacon cannot shift when something happened.

Why /complete can create a row

Because /start might never have arrived. A blocked or dropped start beacon should not also cost you the completion. So /complete is an upsert too, and the resulting row is a real, countable finished game that simply has no device attached. The dashboard does not hide those or guess at whose they were: it collects them into an "Unattributed" group. Only /start binds a device, so a round with no start belongs to nobody, and saying so is more honest than assigning it to the nearest plausible player.

Sound: the one that isn't about a game

A single upserted row per device holding where they ended up (muted or not) and how many times they changed their mind. Not an event log, because a row per press would be a table that grows forever to answer a question nobody asks twice.

The toggle count is taken from the client rather than incremented server-side (MAX(existing, incoming), not toggles + 1), so a device whose row was wiped comes back with its real local count instead of restarting at one. It is clamped, because it is client-supplied.

Standing rule

sound_prefs is not a measurement of anyone's audio experience, and nothing on the dashboard may quote a percentage off it. A player on a silent phone, a player with the tab muted at OS level, and a player who never noticed the game had sound are all indistinguishable from a device that never toggled. It answers "does anyone touch this button", and nothing more.

Part 05

Why the URLs are so boring

The beacons used to POST to /api/analytics/start, and the admin feed used to read /api/admin/analytics/events. Both were changed, and the reason is the best worked example in this codebase of why a naming decision is an engineering decision.

Ad and content blockers ship filter lists that match request URLs by pattern. analytics, track, collect, beacon, telemetry, pixel, event, visit, view, pageview — a path containing any of those is a path a meaningful share of browsers will cancel before it leaves the machine.

The two failures looked completely different:

Admin feedPlayer beacons
FailureLoudSilent
SymptomA bare NetworkError in the browser, nothing in the Worker logsNothing at all
ConsequenceConfusing but visibleThose players never appeared in any count, ever

The silent one is the dangerous one, and it is dangerous because of the design in Part 03. A fire-and-forget beacon that was blocked in the browser is indistinguishable from one that was delivered. Nothing errors. Nothing retries. Nothing logs. Those players simply were not in the data, and no amount of staring at the dashboard would tell you they were missing.

Hard rule

Never put analytics, event, track, collect, beacon, telemetry, pixel, visit, view or pageview into any URL the browser calls. That last group is exactly why the arrival beacon is named /seated rather than /visit.

Hence /api/rounds/seated, /start, /complete, /share. They read as game vocabulary because game vocabulary is not on anybody's filter list. The public stats endpoint is allowed to be called /api/stats, because shields.io fetches it server-side and no browser extension is involved.

Part 06

The trust boundary: who is allowed to say what

These endpoints are public and unauthenticated. Anyone can POST to them with curl. That is the same trust model as the rest of the game (the reveal is client-initiated, the archive is client-tracked, it is a Wordle-style game and not a bank), but "unauthenticated" is not the same as "unvalidated". Every field falls into one of three categories.

Category one: the client says it, the server checks the shape

Ids, dates, enums, counters. A single validator guards every round beacon:

// worker/routes/analytics.ts — the shared validator
function base(body: unknown): Base | null {
  const b = body as (Partial<Base> & { kind?: string; surface?: string }) | null;
  if (!b || typeof b.roundId !== "string" || b.roundId.length < 8 || b.roundId.length > 64) return null;
  const puzzleNumber = Number(b.puzzleNumber);
  if (!Number.isInteger(puzzleNumber) || puzzleNumber < 0) return null;
  if (typeof b.date !== "string" || !isValidDateString(b.date)) return null;
  // Older clients omit `kind`; treat those as the daily. Anything
  // not in the enum is rejected outright.
  const kind = b.kind === undefined ? "daily" : (b.kind as RoundKind);
  if (!ROUND_KINDS.includes(kind)) return null;
  const surface = b.surface === undefined ? "web" : (b.surface as Surface);
  if (!SURFACES.includes(surface)) return null;
  return { roundId: b.roundId, puzzleNumber, date: b.date, kind, surface };
}

Anything that fails gets a 400 and is never stored. Note the two undefined defaults: they are backwards compatibility for old clients that predate the kind and surface columns, and they are the only place absence is tolerated.

Category two: the server stamps it, the client never sees it

Two values are never accepted from the browser at all.

The country. Cloudflare's edge resolves it for every request that reaches a Worker, so the handler reads it off the request rather than the payload. Nothing to spoof, no extra bytes on the wire, and no IP address is stored anywhere. Two special values come back from Cloudflare and are kept as-is: T1 for a Tor exit node and XX for "could not determine".

function countryOf(c: Context<{ Bindings: Env }>): string | null {
  const cf = (c.req.raw as { cf?: { country?: unknown } }).cf;
  const raw = typeof cf?.country === "string" ? cf.country : c.req.header("CF-IPCountry");
  const code = raw?.trim().toUpperCase();
  return code && /^[A-Z0-9]{2}$/.test(code) ? code : null;
}

The calendar day on a visit row, via serverToday(). A visit belongs to the day it happened on, and letting a client with a wrong clock decide that would put arrivals on days that had not started yet.

Category three: the client supplies it, the server re-derives it

Exactly one field is in this category: source. It is the only value on any beacon that starts life in a URL the player controls, so the Worker re-normalises it regardless of what the client claims to have already done. Lowercased, matched against /^[a-z0-9][a-z0-9_.-]*$/, capped at 32 characters, and anything that fails becomes the literal direct.

The client-side normalisation exists to survive an in-app navigation, not to be trusted. The server's pass is the authoritative one. That is a general pattern worth internalising: shared validation code does not mean shared authority.

Also worth knowing

Analytics may never break gameplay, and this is enforced structurally rather than by discipline. Resolving which dish a round played is a database lookup that could fail, so it is wrapped in a try/catch that returns null on any error. A round with an unknown dish is a small gap in one chart. A round that crashed the beacon handler would be a 500 the player never sees but the row never records.

Part 07

Where it lands: three tables and an upsert

The database is Cloudflare D1, which is SQLite. Four tables hold everything discussed here.

Idempotency is the design, not a feature

Look at the uniqueness column again. Every single table is keyed so that writing the same fact twice is harmless. This is not incidental tidiness — it is the direct consequence of fire-and-forget delivery. When you cannot retry, cannot confirm and cannot detect a duplicate at the sender, the receiver has to be built so that duplicates cost nothing.

Here is what the arrival insert looks like with that principle applied:

INSERT INTO analytics_visits (visit_day, player_id, surface, country, source, first_seen_at)
VALUES (?, ?, ?, ?, ?, datetime('now'))
ON CONFLICT(visit_day, player_id) DO NOTHING

DO NOTHING encodes a policy: first touch of the day wins. A device that opened the game directly this morning and clicked an ad at lunch keeps direct, because the ad did not bring them here today. Change that one clause to DO UPDATE and you have silently switched the whole product to last-touch attribution.

And here is the completion upsert, where the policy is more nuanced:

INSERT INTO analytics_rounds (round_id, puzzle_number, play_date, kind, surface,
    country, dish_id, started_at, guesses, solved, completed, completed_at, updated_at)
VALUES (?, ?, ?, ?, ?, ?, ?, datetime('now'), ?, ?, 1, datetime('now'), datetime('now'))
ON CONFLICT(round_id) DO UPDATE SET
  guesses      = excluded.guesses,
  solved       = excluded.solved,
  completed    = 1,
  completed_at = COALESCE(analytics_rounds.completed_at, excluded.completed_at),
  updated_at   = excluded.updated_at

Read the DO UPDATE block as a list of decisions. Results are overwritten. completed_at is coalesced so the first completion time survives a replay. And the columns that are absent from the block — kind, surface, country, dish_id — are the insert-only ones from Part 04.

Schema evolution: additive, always

The analytics schema was not designed up front. It grew, one column at a time, and every migration is additive because production D1 is the only copy of this data and there is no automatic backup. The history is legible in the migration list and it doubles as a record of which questions became askable when:

The consequence to remember

Every one of those columns is NULL for every row written before it existed. That NULL means we were not measuring yet, and it must never be read as a zero or as a category. A round with a NULL country is reported as untracked, not as an unknown country. Rows with a NULL dish are untracked, not assigned to a dish. This is the single most common way an analytics dashboard starts lying, and Part 11 is entirely about it.

Part 08

Two ledgers: sending versus counting

This pattern appears twice in the codebase and is worth naming, because it is the thing designers usually get wrong when they specify "only show this once".

There are two separate questions, and one mechanism cannot answer both:

  1. Should I send this? Answered on the client, in sessionStorage, instantly and offline.
  2. Should I count this? Answered by the database's primary key, authoritatively and permanently.

For arrivals, the client ledger is a sessionStorage key holding the day it last reported. If it matches today, no beacon is sent:

export function markSeated(day: string): boolean {
  try {
    if (sessionStorage.getItem(SEATED_KEY) === day) return false;
    sessionStorage.setItem(SEATED_KEY, day);
    return true;
  } catch {
    // Storage blocked — send it and let the server's primary key dedupe.
    return true;
  }
}

Neither ledger is sufficient alone. sessionStorage is per-tab and cleared constantly, so it can never be the source of truth for a visitor count. But without it, every mode switch (which navigates by assigning a URL and remounts the whole page) would fire a redundant request. The failure mode of the pair is one wasted HTTP request, never a missed visitor.

Look at the catch branch: storage blocked means send it anyway. When in doubt, the client sends and the server deduplicates, because the server's ledger is the one that is actually correct.

The announcement modal uses the identical structure for a different reason: localStorage decides what to show so the modal can open with no round-trip, while announcement_views counts who was reached. And that view is recorded on display rather than on dismissal, because reach means somebody saw it, not that they agreed with it.

Part 09

Time: stored in UTC, true in New York

The puzzle rolls over at midnight Eastern for everybody on Earth. Not the browser's local midnight, not UTC. That single design decision creates the most persistent complication in the read path.

Timestamps are written by SQLite's datetime('now'), which is UTC. SQLite has no named-timezone support: it cannot be told about America/New_York, cannot apply daylight saving, cannot group rows into Eastern days. So the conversion cannot happen in SQL and has to happen in JavaScript.

The technique is to have SQL do the part it is good at — grouping — at a resolution fine enough that the conversion is still possible afterwards:

SELECT strftime('%Y-%m-%d %H', started_at) AS bucket, kind, COUNT(*) AS started
FROM analytics_rounds
WHERE started_at IS NOT NULL
GROUP BY bucket, kind

SQL returns UTC hour buckets. JavaScript then folds each bucket into the Eastern day and hour it belongs to, using Intl.DateTimeFormat with the game's timezone, which handles daylight saving correctly by definition. An hour maps cleanly onto one Eastern hour because the offset is a whole number of hours in both DST phases.

Two consequences follow from this that are easy to miss:

  • A day slice queries a ±1 day window. One Eastern day straddles two UTC days, so asking for "22 July" pulls a wider window from SQL and drops the out-of-range rows during the fold, where the conversion is actually possible.
  • The visits table is the exception. Its visit_day was stamped by the Worker as an Eastern day at write time, so it needs no fold at all. That is one of the reasons the day is stamped server-side rather than derived later.

One more timing subtlety: "games started" is measured by when the round started, not by which puzzle it was. An archive replay of an old puzzle played today lands on today's bar in the daily chart, not on the old puzzle's date. The row carries both facts (play_date and started_at) precisely so each chart can pick the one it means.

Part 10

The read path: query, fold, render

Writing is many tiny requests. Reading is the opposite: one authenticated admin request that issues a whole batch of SQL at once and then transforms it in pure functions.

GET /api/admin/analytics fires fourteen prepared statements in a single DB.batch() call. Each one is shaped to feed a specific fold, and several are deliberately shared between two folds so a second table scan is not paid for twice. The route's job ends there. It does not compute anything.

The architectural rule

Query in the route, fold in the module, assert on the fold

Every transformation lives in its own module as a pure function that takes rows and returns a shape. No database access, no request object, no clock unless it is passed in as an argument. Each has a unit test file sitting next to it. This is why the numbers can be trusted: the interesting logic is all testable without a database.

There are a dozen of these fold modules, and their names map almost one-to-one onto dashboard panels:

The surface filter

Every tab can be scoped to web, Discord or both. That is implemented as a tiny helper returning a SQL fragment appended to each statement. One deliberate exception: the query that determines when device tracking switched on is never surface-filtered, because it marks the instrument rather than the audience, and letting a filter move it would make the Discord view claim measurement started later than it did.

The public read

A separate, unauthenticated, aggregate-only route serves /api/stats for the README badges, /api/stats/breakdown for the public case-study page (edge-cached for ten minutes), and /api/stats/badge in shields.io's schema. It sends Access-Control-Allow-Origin: * and exposes nothing per-player and no guess content. Its definitions deliberately mirror the admin ones so the two can never disagree in public.

Part 11

The honesty rules

This is the part that is really design work rather than engineering. A pipeline that collects correct data can still produce a lying dashboard, and at this game's volume (tens of rounds a day, not thousands) the ways it lies are specific and predictable. Seven rules govern it.

1. Never report unmeasured as zero

The most important one. A visit count of null means the arrival beacon had not shipped yet on that day. Rendering it as 0 would claim a hundred percent bounce rate for the game's entire early history. Every fold that can encounter a gap distinguishes "we did not measure" from "it was none", and panels omit a row rather than draw an empty one.

2. Every small-sample rate carries its interval

Below 30 observations, a percentage is a mood rather than a measurement. "67% win rate" off three completions and off three hundred render identically and mean completely different things — the first moves 33 points if one more player loses. So every rate whose denominator is under 30 is quoted with a 95% confidence interval, and nothing above 30 is.

The interval is a Wilson score interval rather than the textbook normal approximation, because this game lives exactly where the normal approximation breaks: tiny samples, and rates pinned near 0 or 1 (almost nobody shares, almost everybody solves). The normal approximation returns a zero-width interval at 4-of-4, which is the most confident-looking and least justified output possible.

3. A headline refuses to compare when it cannot

The dish report, the arrival-source table and the experiment verdicts all check whether two intervals actually separate before claiming a difference. "Too early to tell" is a verdict, not an absence, and every undecided one is shipped alongside an estimate of how many more days it needs.

4. Censored denominators

Return rates only count a device once seven days have passed since the visit being measured. Everything more recent is reported as pending, never as a no-show. Without this, a busy week lowers your retention number and an ad campaign lowers its own score with every click it buys, because the newest arrivals have not had time to come back yet.

5. Pool over a period, never average the days

A rate for a week is the week's successes over the week's trials. It is never the mean of seven daily percentages, because that lets a one-round Tuesday outvote a busy weekend. This is also why the experiment series ships raw counts rather than percentages: a pre-divided number cannot be re-pooled over a different window.

6. Broken measurements are dropped, never clamped

A negative duration (a /start that arrived after its /complete) is dropped, not clamped to zero. A round left open in a background tab all morning is capped at 15 minutes for the play-time total, and a capped flag rides along so the panel states that the trim happened rather than hiding it. A ratio over 100% is printed honestly; only the bar drawing it is clamped.

7. A duration needs both ends measured

Completion timestamps are never substituted with the row's updated_at. A round missing one end shows a marker and the words "time not recorded". An abandoned round gets no duration at all, because now-minus-start measures how long ago something happened, not how long anyone played.

And solve times are reported as a median and p90, never a mean. A round is a browser tab, and tabs get left open.

Why this belongs in a document about beacons

Because every one of these rules is a downstream consequence of how the data arrives. Fire-and-forget delivery creates gaps. Additive migrations create nulls. A small player base creates small denominators. Anonymous devices create ambiguity about what a "player" is. The honesty rules are not decoration on top of the pipeline; they are the pipeline's failure modes, handled in the open.

That last row is worth expanding, because it is the only destructive operation in this whole system. GET /api/admin/device-data reviews every row belonging to this browser across all three tables, and DELETE on the same path removes them. The review is a mandatory step, not a suggestion: the delete button does not exist until the summary has loaded, because production has no automatic backup. The delete then reports what each table actually lost rather than what was asked for, so a wipe that matched nothing tells you that you had the wrong id. And the device id itself survives, because nothing touches localStorage — the next round records under the same id.

Part 13

Tracing one round end to end

Everything above, as a single narrative. Somebody clicks a link in a newsletter on a Tuesday evening.

  1. The page loads at /?utm_source=newsletter. Before React mounts, a module-level constant reads utm_source, normalises it to newsletter and stashes it in sessionStorage. Another constant checks for frame_id, finds none, and fixes the surface as web for the rest of the tab.
  2. The board resolves. tracked is true (not a preview, not a playtest). One effect mints a round_id and saves it with the round. Another checks the seated ledger, finds no entry for today, and fires POST /api/rounds/seated with a device id, web, and newsletter.
  3. The Worker validates the device id, re-normalises the source, reads the country off Cloudflare's edge, stamps today's Eastern date, and inserts a row into analytics_visits. If the player had already arrived today, DO NOTHING silently discards it.
  4. First guess. Wrong, but a clue ticket prints. POST /api/rounds/start fires with the round id, puzzle number, date, daily, web and the device id. A new row appears in analytics_rounds with a UTC started_at, a resolved dish_id and a country.
  5. Guesses two through four send nothing. Guesses are gameplay requests, not beacons, and no guess content is ever recorded anywhere.
  6. They solve it on the fifth. POST /api/rounds/complete carries guesses: 5, solved: true. The upsert finds the existing row, writes the results, sets completed_at, and leaves kind, surface, country and dish exactly as /start left them.
  7. They share the grid. POST /api/rounds/share sets shared = 1 and shared_at. Pressing share again changes nothing.
  8. The next morning the admin opens the dashboard. Fourteen statements go out in one batch. The UTC timestamp on that round is bucketed to its hour, folded into Tuesday Eastern, and lands in the 7pm column of the service chart, in Tuesday's bar on the growth series, in the "5 guesses" column of the distribution, and in the newsletter row of the arrival table — where its return rate is reported as pending, because seven days have not passed yet.

One arrival, one game, four small POSTs, two rows in a database, and a dozen numbers on six tabs. The whole system is that shape repeated.

The panels those numbers land on are covered in Admin Analytics Dashboard, and the other surface firing these beacons in Discord Activity Integration.

The five things to remember

  1. Fire and forget is the root cause of everything else. Because a beacon cannot be retried, confirmed or even known to have failed, every table is keyed to make duplicates harmless and every read has to cope with gaps.
  2. Where a value is minted decides who can lie about it. Ids from the client, day and country from the server, and exactly one field re-derived on arrival because it started in a URL.
  3. Three units, never blurred. Rounds, devices, visits. Naming the wrong one is how a chart becomes wrong while every number in it is right.
  4. Null means unmeasured. Not zero, not unknown, not a category.
  5. Query in the route, fold in the module. Every transformation is a pure function with a test beside it, which is the reason any of these numbers can be trusted.

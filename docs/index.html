Lunch Special

A daily dish-guessing game set in the golden age of diners.

Six guesses to name the day's Special. Every guess is a real dish, and the game reports what that dish has in common with the answer. This page covers how the feedback system was designed, how the thing is built and deployed, and what the live analytics say about its difficulty.

The design problem Premise

I consider cooking to be one of my biggest hobbies, so I wanted to bring my love of food into a game that can teach people more about the dishes they enjoy everyday.

That premise breaks the format it borrows from. Wordle's feedback is positional: a word is an ordered list of letters, and the colours mean right letter, right slot. A dish has no slots. "Pad Thai" and "Bibimbap" don't line up character by character in any way a player cares about. So the feedback language had to be designed from scratch.

Constraints

  • Readable at a glance, mid-round, without parsing prose.
  • Expressible as emoji — if the result can't be posted as a spoiler-free grid, the game has no distribution.
  • Narrowing enough that a 283-dish space collapses within six guesses.
  • Fair to a player who has never heard of the answer.

The last one drove the rest. Wordle can be pure deduction because every English speaker owns the whole answer space. Food knowledge isn't distributed that way. So the game runs two feedback channels at once: one deductive, one that gives information away outright.

The gameplay loop 6 guesses · 5 clues

Each miss costs a guess and reveals a clue, so difficulty falls as the round goes on. A daily game that regularly sends players away with nothing doesn't get opened again.

Channel one — deduction

Each guess is scored on four categorical attributes plus a set intersection over ingredients. Country is the only attribute with a middle state: same country is a hit, different country in the same region is a near-miss. That one warm signal is what makes geographic triangulation work.

Country · hit Country · same region Course · miss Temp · miss Protein · hit

Ingredients report as n of m matched — never which ones, or the answer leaks.

Channel two — the clue ladder

Five clues per dish in a fixed rhetorical order, so difficulty falls predictably. The same ladder applies to all 283 dishes, which turns clue writing into a repeatable job instead of 283 separate creative problems.

Rungs, revealed after misses 1–5
1 Broad geography
2 Origin and history
3 What made it famous
4 A key ingredient or technique
5 Near-giveaway — everything but the name

The share card came first

The emoji grid was specified before the feedback system, because it constrains what the feedback can be. Four tiles per row, one pantry count, no dish names.

Three modes, one engine

One round resolver serves all three. They differ only in how the target is picked and what gets written down afterwards, which is why adding modes cost almost nothing.

Mode Target Counts to streak
Today's Special Scheduled dish for today Yes
Leftovers Any past day No — saved per date
Chef's Choice Random dish, seeded No

Replays must not be able to inflate a streak. Sealing lifetime stats off from the archive is what makes the archive safe to offer at all.

The stack 4 runtime deps

The whole thing is one Cloudflare Worker. It serves the React bundle, answers the API, and queries a SQLite database on the same platform. No second service, no container, nothing to keep warm, and one deploy command that can't half-succeed.

Trade-off

The client is trusted with round bookkeeping — the reveal is client-initiated after game over, like Wordle. Anyone determined can read the answer out of a network tab. Closing that means server-side sessions, which means identity, which means accounts. The cheat is self-punishing; the account system wouldn't be.

How the content is organised to iterate fast 3 tables

A daily game consumes a piece of authored content every 24 hours, indefinitely. The engine took a few days; what determines whether the game keeps running is how cheap it is to add the 284th dish. So the data model is built around one question: what is the smallest correct unit of content, and can the system tell me when one is malformed before a player sees it?

Table 1

dishes

Name, country, region, three enums — course, temperature, protein — and a JSON array of canonical ingredients.

283 rows · 58 countries · 9 regions

Table 2

clues

Five per dish, each stamped with its rung. A unique constraint on (dish, rung) makes a duplicated rung impossible.

1,415 rows · exactly 283 × 5

Table 3

schedule

One date, one dish. Deliberately thin — it holds no game state, so rescheduling is a one-row edit.

Date format enforced by a GLOB check

The invariant that does the most work

A dish is schedulable only with at least 3 ingredients and exactly 5 clues. That rule is enforced in the scheduling endpoint, shown as a badge in the admin UI, and checked in CI. A half-written dish can sit in the pool indefinitely with no risk of landing on a live date.

Every enum is a column-level CHECK, so a mistyped region is a failed insert rather than a grey tile that never matches anything.

Ingredients are a controlled vocabulary

Matching is a set intersection on raw strings, so tomato and tomatoes are two different foods as far as the game is concerned. The vocabulary is canonical — lowercase, singular — and the admin editor autocompletes from what exists rather than letting me coin a new spelling by accident.

Dull, but it's the difference between feedback that feels sharp and feedback that feels broken.

Four authoring paths, one catalogue

Path Used for How it works
Admin CMS Editing one dish, fixing a clue Password-gated app at /admin. The dish editor renders a live preview using the real game components, so a clue is read in the ticket it will appear in, not in a text field.
Batch SQL Adding 50 dishes at once A written spec in the repo defines every field's rules, so a batch is mechanical to produce and mechanical to check. Three migrations are 50-dish drops.
Player requests Finding out what people want A suggestion form on the end-of-round receipt writes to a separate inbox table. One click promotes a request into a prefilled dish editor.
Auto-fill Filling the calendar Picks least-recently-served schedulable dishes and skips anything served in the last 60 days. Scheduling a month is one button, not thirty decisions.

The seed / migration split

There are two representations of the catalogue, doing different jobs. seed/seed.sql is the canonical, diffable source of truth — it deletes and rebuilds everything, which is right for a fresh local database and catastrophic against production, where it would erase every edit made through the admin. Production only receives additive migrations: inserts only, dishes keyed by slug rather than hardcoded id, applied automatically on release and never re-run.

A path-filtered CI job validates the catalogue against the real schema constraints whenever a migration or the seed changes, so a mistyped enum fails on the pull request rather than on the day that dish is the Special.

Development to production git tag → live

Releases are cut by pushing a version tag. Everything after that is automated, gated on the same checks I run locally, and ordered so the database is migrated before the code that expects the new columns goes live.

  1. Local dev against the real runtime Vite serves the client while the Worker runs in workerd against a local D1 file. A separate free-play entry point opens a fresh round on a random dish, so I can test the loop repeatedly without burning the day's puzzle or writing to stats. npm run dev · npm run play
  2. Gate locally Unit tests cover the pure logic — feedback scoring, puzzle numbering, date validation, the deterministic fallback pick, and the shaping of the public analytics breakdown. Keeping that logic free of I/O is what makes it testable: the aggregate queries can't run without a database, so the code that folds their rows into a response was split into a pure function that can. Then a strict TypeScript build across three composite projects. Worker code compiles without DOM types, so a stray window in an API handler fails the build. npm test && npm run check
  3. Pull request — data integrity CI Path-filtered: it fires only when migrations, the seed, or the integrity test change, so routine commits aren't taxed but bad content can't merge. .github/workflows/ci.yml
  4. Tag the release Any v* tag triggers the deploy workflow. A concurrency group makes two deploys unable to race. The changelog is generated from the merged PRs' labels, so it's a by-product of the label each one already carries, not a document kept in sync by hand. git tag v1.1.0 && git push origin v1.1.0
  5. CI regenerates, re-tests, migrates, deploys Cloudflare's runtime types are generated rather than committed, so CI rebuilds them first, re-runs tests and the typecheck, applies pending D1 migrations to production, then builds and deploys. Migrations before deploy, never the reverse. cf-typegen → test → check → d1 migrations apply --remote → deploy
  6. Live on the custom domain The same artefact serves the public site and the Discord Activity, so the two surfaces can't drift apart. lunchspecial.app

Secrets never reach CI

The admin password and the token-signing key are set directly on the Worker and persist across deploys, so the build pipeline has no access to either. CI holds only its own Cloudflare deploy credentials. The type generator reads a placeholder file, because it needs the shape of the environment, not the values.

What CI deliberately won't do

It never runs the seed. Seeding is destructive by design, and automating a destructive step against production is how you lose a month of content edits. It stays a manual, once-per-environment bootstrap step.

Dependencies update on a schedule

Four runtime dependencies means nearly all the churn is tooling — the bundler, the Workers CLI, the test runner — plus the pinned action versions in the workflows. Dependabot opens grouped weekly pull requests for those, so the same local gate and typecheck decide whether a bump is safe and the ordinary tag-to-deploy flow ships it. Grouping is the point: a couple of tidy PRs a week instead of one per package.

Security scanning on every pull request

CodeQL runs its security-and-quality queries over the TypeScript on every PR — not path-filtered like the data-integrity job, because a logic change anywhere is what it looks at. It needs no build step: it reads the source directly, which sidesteps the generated Cloudflare types the real build depends on. Free on a public repo, with results in the repository's Security tab.

Instrumentation, and what it says Live production data

A daily puzzle has one main tuning knob — difficulty — and no way to judge it from the inside, so the game was instrumented before launch. The engagement charts here read live from the production database — 154 rounds from 43 devices so far. It is still an early, self-selected sample, so treat it as a method and a first read, not a result.

How the telemetry works

One row per round, created by a fire-and-forget beacon when the board opens and updated twice after. No accounts, no guess content, no personal data — the player id is a random value generated on the device, and its only job is to separate a returning player from a new one.

What the distribution shows

Mean solve is 2.8 guesses, and the sixth is almost never needed. 78% of solves land by guess three, so most players see clue rungs 1 and 2, some see 3, and rungs 4 and 5 are rarely reached — 566 clues that almost nobody reads.

That's a difficulty problem showing up as a content-budget problem. The fix isn't more clues: either the pool gets harder (it currently skews toward globally famous dishes, which is what a launch needs), or the guess budget shortens and the ladder recompresses. The instrumentation to measure either change is already in place.

Instrumentation bug: blocked beacons

The beacons originally posted to paths containing the word analytics. Ad blockers ship filter rules for that path shape, so in a meaningful slice of browsers the requests were cancelled before they left the page. The admin dashboard failed loudly — a bare network error with nothing in the server logs. The player beacons failed silently: they're fire-and-forget, so a blocked beacon is indistinguishable from a delivered one, and those players never appeared in any count.

Missing data biased toward the technical users most likely to block things is worse than wrong data, because nothing looks broken. The fix was renaming the endpoints to something boring, and writing the rule into the project docs: no client-called URL may contain analytics, event, track, collect, beacon, telemetry, or pixel. The admin client also now translates a rejected request into a message naming content blockers as the likely cause.

Trade-offs Decisions worth naming

The day rolls over at one fixed time worldwide

Not the player's local midnight, not UTC — a single timezone shared by client and server. Everyone is on the same puzzle at the same moment, so a result posted in a group chat is about the same dish. The alternative hands a player in Sydney the answer to a puzzle a player in Los Angeles hasn't started.

An unscheduled day still gets a Special

If the calendar has a gap, the game hashes the date and picks deterministically from the active pool — same date, same dish, for everyone. The failure mode for forgetting to fill in a month is a less curated puzzle, not a 404.

Future dates are refused server-side

The archive plays backwards to puzzle #1, but a request for tomorrow is rejected — with a two-day tolerance so a skewed device clock or a request landing on the rollover boundary doesn't lock out a legitimate player. Spoiler protection has to live on the server, because the client is the part you can't trust.

The archive can't touch your streak

Replays are stored per date, outside lifetime stats. It costs nothing to implement and it's the only reason the archive can be generous.

Discord added no build complexity

The Activity works because the app is same-origin and self-contained — every API call relative, every font and image served by the same Worker. Discord's proxy rules were satisfied by decisions made for other reasons. Inside the embed the share button routes through Discord's own share command, because the iframe has neither clipboard nor share permission.

A share failure is never silent

Sharing returns three states rather than a boolean: shared, unavailable, or failed. Only unavailable falls back to the web path, because inside Discord that path is a dead end that rejects quietly and leaves the button looking untouched. A real failure changes the button label instead.

What's next In priority order

  • Recalibrate difficulty. The 2.8-guess mean says the pool is too easy. Tag dishes with a difficulty estimate, schedule a curve across the week, watch the distribution move.
  • Reclaim the unused clue rungs. Either shorten the guess budget so later rungs are reachable, or spend that authoring effort on more dishes instead.
  • Find where the 27% leave. First guess, third, or before guessing at all — the distinction changes the fix completely, and it isn't measured yet.
  • Unify identity across surfaces. Storage inside Discord is sandboxed to Discord's origin, so an Activity player has a separate history from the same person on the web. Solving it properly means optional accounts, which trades against the no-signup premise — worth doing only once the Discord numbers justify it.

Overview the short version

  1. 01 Food doesn't support Wordle's feedback grammar, so I designed a different one. Two feedback channels, one deductive and one that concedes information as you fail, with the shareable result card specified before either of them.
  2. 02 The clue writing is a system rather than 351 separate creative problems. Every dish is written against the same five-rung ladder, which is what makes a daily content requirement sustainable for a single author.
  3. 03 The game is one part of a live-service loop I built to operate it. An authoring CMS, a scheduler, a suggestion inbox, an announcement channel, telemetry, and an experiment log, connected as a single loop from idea to verdict.
  4. 04 The instrumentation is designed to report its own limits. Small samples carry their confidence intervals, unmeasured periods are never drawn as zero, and "too early to tell" is one of four verdicts the comparison can return.
  5. 05 A scheduling change was logged, shipped, and then shown to have worked. Finish rate moved from 81% to 91% with non-overlapping confidence intervals — and read over a shorter window, the same change would have reported nothing.

The design problem feedback design

Cooking is my biggest hobby, and I wanted a game that teaches people something about the food they already eat. That premise breaks the format it borrows from. Wordle's feedback is positional: a word is an ordered list of letters and the colours mean right letter, right slot. A dish has no slots, and "Pad Thai" and "Bibimbap" do not line up character by character in any way a player would care about.

Constraints, set before anything was built

  • Readable at a glance, mid-round, without parsing prose.
  • Expressible as emoji — a result that can't be posted as a spoiler-free grid gives the game no distribution.
  • Narrowing enough that a 351-dish space collapses inside six guesses.
  • Fair to a player who has never heard of the answer.

The fairness constraint drove the rest. Wordle can be pure deduction because every English speaker already owns the entire answer space; food knowledge is not distributed that way, and a player in Ohio and a player in Lagos begin a round on Shakshuka in genuinely different positions. The game therefore runs two feedback channels at once: one that rewards deduction, and one that concedes information as you fail, which is the subject of the next section.

Channel one — deduction

Every guess is a real dish, scored on four categorical attributes plus a set intersection over its ingredients. Country is the only attribute with a middle state: the same country is a hit, and a different country in the same region is a near-miss. That single warm signal is what makes geographic triangulation possible.

Country · hit Country · same region Course · miss Temp · miss Protein · hit

Ingredients report as n of m matched, never which ones, or the answer leaks.

Takeaway

The problem was not to reskin Wordle for food, but to build a feedback language for a domain where players do not share a vocabulary.

Narrative and content design 1,755 clues · one ladder

A daily game consumes a piece of authored content every 24 hours, indefinitely. Approaching 351 dishes as 351 individual creative problems becomes unsustainable within a month or two. The clue set is therefore organised as a fixed dramatic order: the same five rungs for every dish, descending from geography to near-giveaway.

The ladder, revealed one rung per miss

# Rung What it's doing dramatically
1 Broad geography Narrows the map without naming a country.
2 Origin and history The first rung with a voice, where the dish stops being a puzzle token and starts being from somewhere.
3 What made it famous The film, the street, the argument over who invented it. The rung people remember afterwards.
4 A key ingredient or technique Converts knowing about the dish into being able to name it.
5 Near-giveaway Everything but the name. Missing at this point should feel unlucky rather than unfair.

The same ladder, 351 times over. Writing clue 3 for Pierogi is the same task as writing clue 3 for Ceviche, and a repeatable task is one that can still be done in month six.

The fiction carries the interface

Each piece of UI is named for what it would be in a diner, and the names do explanatory work that would otherwise fall to a tutorial. A player already understands what a receipt is for.

The share card was specified first

Before the feedback system and before the schema. A daily game with no shareable result has no distribution, and what the emoji grid can express is a hard constraint on what the feedback is permitted to be: four tiles per row, one pantry count, no dish names, and nothing that spoils the answer.

For most people this card is the only part of the game they will ever see, which is a reasonable argument for designing it before the system that produces it.

Takeaway

Narrative design here is a production system: a fixed dramatic order that makes 1,755 clues writable at a steady rate, and a fiction that absorbs most of the tutorial.

Three modes, one engine

One round resolver serves all three. They differ only in how the target is picked and what's written down afterwards, which is why adding a mode costs almost nothing.

Mode Target Counts to streak
Today's Special Scheduled dish for today Yes
Leftovers Any past day No — saved per date
Chef's Choice Random dish, seeded No

Replays must not be able to inflate a streak, so lifetime stats are sealed off from the archive. That is what makes the archive safe to be generous with.

One rollover time for the whole world

The day turns over at a single named timezone shared by client and server rather than at each player's local midnight, so everyone is on the same dish at the same moment and a grid posted in a group chat refers to the puzzle everyone else is playing. Local midnight would hand a player in Sydney the answer to a puzzle Los Angeles has not started.

The archive plays backwards to puzzle #1, but the server refuses a request for tomorrow, with a two-day tolerance so a skewed device clock cannot lock out a legitimate player.

Takeaway

Three modes share one resolver and one clock. What varies between them is only what gets written down afterwards.

Live-service loop author → measure → ship

The game engine took a few days. Everything since has been the apparatus around it, on the principle that a daily game is not something you finish but something you operate. Each station below was built because the one before it started raising questions I had no way to answer.

One turn of the loop

  1. AuthorA dish and its five clues, written in the admin CMS against a live player preview.
  2. ScheduleBooked onto a date, 30 days ahead, by autofill or by hand.
  3. PlayServed to the website and the Discord Activity from one build.
  4. MeasureFour anonymous beacons: arrived, first guess, game over, share.
  5. HypothesiseA change logged with the metric it should move, named before it ships.
  6. ShipA version tag runs the tests, migrates the database, and deploys.

Each station is a piece I built in response to the one before it, in the order shown.

What sits on each station
Station What I built Why it had to exist
Author Admin CMS with a live player preview; a batch-SQL spec; a suggestion inbox A clue has to be read in the ticket it will appear in, not in a text field. Player suggestions from the end-of-round receipt promote to a prefilled editor in one click — five dishes on the menu arrived that way, and get credited on the check when they come up.
Schedule Calendar, 30-day autofill, a schedulable invariant Autofill takes least-recently-served dishes and skips the last 60 days, so booking a month is one button rather than thirty decisions. Nothing reaches a live date without ≥3 ingredients and exactly 5 clues.
Play One resolver, three modes, two surfaces One build serves the website and the Discord Activity, so they cannot drift.
Measure Four anonymous beacons; a six-tab dashboard Arrival, first guess, game over, share. Every tab holds one question rather than one data source — what's live, what the menu is doing, who's playing, what's changing, did I cause it, and the raw feed.
Hypothesise An experiment log with the metric named up front What the change was, what I expected, the day it shipped, and which metric it should move. Chosen afterwards, the metric is whichever of the eight happened to move most, which is not evidence of anything.
Ship Tag-triggered CI: test, typecheck, migrate, deploy Migrations run before the code expecting the new columns. Secrets live on the Worker and never reach CI.

Reaching players with no audience list

Without accounts there is no mailing list and no push token, so the only reliable moment of attention is the few seconds after someone opens the app. The announcement system exists to ration that moment: never before the game itself, once per player, one card at a time, with the header capped at 60 characters so it cannot grow into a changelog.

Takeaway

The deliverable is not only the game but the loop around it, which can carry a change from an initial hypothesis to a measured verdict without a second person involved.

Technical architecture 4 runtime deps

One Cloudflare Worker serves the React bundle, answers the API, and queries a SQLite database on the same platform. No second service, nothing to keep warm, one deploy that can't half-succeed. Every choice below was made to keep the distance between "I have an idea" and "it's live and being measured" as short as one person can make it.

Only /api/* wakes the Worker; everything else is served from the asset layer. The board is a static file, and only guesses cost anything.

Choices, and what each one bought the design loop
Choice What it bought
The Worker runs in the real runtime locally Local and production execute the same engine, so there is no mock API to drift and playtesting is accurate. This is the main reason a change can go from idea to live in an evening.
D1 (SQLite) with real constraints Every enum is a column-level check, so a mistyped region is a failed insert rather than a tile that silently never matches anything.
No accounts — player state in local storage No sign-up friction, no personal data, no auth surface to defend. The costs are real: stats do not follow a player between devices, and every audience figure on this page counts devices rather than people.
Discord Activity on the same deploy Discord frames the live site through its proxy, and the only Discord-specific code is one dynamically-imported file. The second surface cost one file rather than a second product.

Releases are cut by pushing a version tag. CI re-runs the tests and typecheck, applies pending database migrations, then deploys — migrations first, so the schema is never behind the code expecting it. The tests cover the pure logic: feedback scoring, date validation, and every analytics fold on this page. Keeping those folds free of I/O is what makes them testable, since the queries need a database and the arithmetic does not.

Trade-off worth naming

The client is trusted with round bookkeeping, and the reveal is client-initiated after game over, as it is in Wordle. Anyone determined can read the answer out of a network tab. Closing that would require server-side sessions, and therefore accounts. The cheat costs one player their own round; the account system would cost every player something.

Takeaway

Four runtime dependencies and one deployable artefact, kept deliberately unambitious so that the time goes into the menu instead.

Instrumentation 4 beacons · no accounts

A daily puzzle has one main tuning knob — difficulty — and no way to judge it from the inside, so the game was instrumented before launch. The hard part was never collecting the data. It was building an instrument that admits what it doesn't know.

What one player generates

arrived opened the game,
once per day
→
started first guess
submitted
→
finished guesses used,
won or lost
→
shared result posted

No accounts, no guess content, no personal data, no IP stored. The player id is random and generated on the device, and its only purpose is distinguishing a returning player from a new one. Every write is keyed on the round, so a replayed beacon cannot double-count.

Unmeasured is never drawn as zero

Each instrument switched on at a different time. Days before the player id existed carry null rather than 0, and days before the arrival beacon shipped omit the funnel's top row rather than drawing it empty. Reporting an unmeasured day as zero would assert a 100% bounce rate across the whole history of the game.

Thin numbers carry their uncertainty

At tens of rounds a day, a 67% win rate drawn from 3 completions and one drawn from 300 render identically and mean very different things. Any rate quoted from fewer than 30 observations shows its 95% interval beside it, and nothing else does — an interval on every number would simply train the reader to ignore them.

Wilson intervals rather than the normal approximation, because this game sits where the approximation fails: small samples, and rates pinned near 0 or 1, where it returns an interval of zero width.

Takeaway

An instrument with no way to report "I don't know" will report something else instead, and that answer is very hard to distinguish from a real one.

Experiment log and results before / after

Every chart above answers what is happening. None of them answers whether I caused it. So the database also holds a change log: one row per deliberate change, recording what I expected and — set before shipping, not after — which metric it was meant to move. The dashboard splits the daily series at the ship date and compares the two halves. At this volume the correct answer is often "not enough data yet", and a comparison with no way to return that will return something else instead. Making it a first-class result is most of the design of this feature.

Verdict as of 10 Aug 2026 · 14-day window

Schedule the menu from the mix panel, not by feel

shipped 26 Jul · metric named up front: finish rate
Moved up

The schedule had always been picked for variety, but by instinct. This is the day I began booking it against the menu-mix panel, which compares the region, course, protein and temperature ratios of what has been served against the pool it is drawn from.

81% to 91% of started rounds reaching game over, across 312 rounds before and 404 after. The bars are 95% intervals, and the test is simply whether they overlap. That is stricter than a difference-of-proportions test, deliberately: the more expensive mistake for a project this size is being convinced by noise, not missing a small effect.

Why the window is fixed in advance

Read at a 7-day window instead of 14, the same comparison returns no change: 84% against 89%, with intervals that overlap. Nothing about the game differs between those two readings, only how much of the surrounding variation each window includes. Choosing the window after seeing the data means choosing the answer, which is why the window and the metric are both recorded before the change ships.

The rules that make a verdict worth anything
The metric is named first Chosen afterwards, the metric is whichever of the eight moved most. Reading a different one than the change was logged against prints a warning.
Rates are pooled, never averaged Total solved over total completed. Averaging daily percentages lets a one-round Tuesday outvote a whole weekend — which is why the series ships raw counts.
Counts and rates get different tests A count's variation is day-to-day spread; a rate's is binomial. Judging a share rate by how much traffic fluctuated answers the wrong question.
The ship day counts as "after" A change that went live during a day affected the rest of it. The window is also clipped at today, since padding it with days that have not happened dilutes the effect.
Takeaway

A change is worth claiming only once it can be separated from ordinary variation, and the system is built to say when it cannot be.

Recent work: the player funnel Aug 2026 · 3 releases

A round counts as started on the player's first submitted guess. That was a deliberate decision, on the grounds that opening a page is not playing a game, and it had a cost I did not anticipate: everyone who arrived and never guessed was invisible. The widest number on the dashboard was games started, with nothing above it, so a change that doubled interest while halving conversion would have looked identical to no change at all.

Three releases, in order

  1. Measure arrivals One row per device per day, fired when a real board is ready and never on a playtest. Session storage decides whether to send; a composite primary key decides what to count. Neither is sufficient alone, because session storage is per-tab and every mode switch navigates by assigning a URL. POST /api/rounds/seated
  2. Draw the funnel the arrivals made possible Arrived, played, finished, then shared or played again, every stage counted in devices. It rides a query the new-vs-returning fold already ran, so it cost no additional database work. Two experiment metrics came with it, which made the conversion question askable for the first time. worker/funnel.ts · pure, unit-tested
  3. Take my own play-testing back out of the numbers At tens of rounds a day, one person testing is a visible fraction of every rate on this page. A morning of reloading to check a change writes arrival rows and nothing else, which reads as pure bounce in the funnel I had just built. The admin panel reviews what this browser has recorded across all three tables and then deletes it. GET then DELETE /api/admin/device-data

The unit switch that makes the arithmetic true

The funnel's first row counts people and the rows beneath it count games. A visit is one device per day, while a start is a round, so dividing one by the other directly would report play rates well over 100%. The top row is devices over devices, and every row names its unit.

A ratio above 100% remains possible, since a round begun at 11:58pm files its start on the following day. The number is left as measured and only the bar is clamped.

The review is a required step

The delete button does not exist until the summary of what it will remove has loaded. Production has no automatic backup, so an irreversible wipe should not be reachable without first showing what it covers.

Takeaway

A definition I still think was correct turned out to be the system's largest blind spot, and finding that mattered more than any single change built on top of it.

Roadmap with target metrics

Each item names the metric it should move before it is built, which is the same rule the experiment log enforces, applied to the roadmap. An item I cannot name a metric for is not ready to be on the list.

Next Metric it should move The reasoning
Give a first-time player a second reason to return tomorrow Days played per device Most devices play once. The streak exists but stays invisible until a player already has one, which is the wrong way round.
Find where the arrivals who never guess get stuck Play rate (played ÷ arrived) Whether they leave at the how-to, the typeahead, or the first empty board changes the fix entirely, and telling those apart is a small instrumentation job.

Solving it properly means optional accounts, which trades against the no-signup premise, and is worth doing only if the Discord half of the audience keeps growing.
Takeaway

The roadmap is ordered by what the measurements identify as the constraint, which is currently retention rather than anything about the puzzle itself.
